## 1. 目的とスコープ(ユーザー発言から推測したもの。要確認)

ユーザーの発言は「デスクトップアプリ化したい。まずは設計を固めたい」のみ。以下は私の推測であり、確認が要る。

- 目的(推測): 今ターミナルで動いているライブ認識デモを、ターミナル操作なしで、友人にも見せられるアプリにする。
- 動機の根拠: 現状の CLI は TTY 必須・メニュー選択式で、起動に `cargo run` が要る。見ている人にとって、画面に出るのは文字の行だけ。
- やらないこと(提案): アプリ内での学習、Windows/Linux 対応、他人への配布(署名・公証)。いずれも後段。

## 2. 現状のコードから分かること(コードで確認済み)

- `pose_extractor` は**バイナリのみのクレート**で、ライブラリではない。`main.rs` は 5172 行、`live.rs` は 2965 行(2026-10-11 時点の `wc -l`。`live.rs` は JSON 入口の追加で増えた分を含む)。
- `live.rs` は、入力元・キー入力・区切り・認識器・画面出力をすでにトレイト(差し替え可能な部品の型)で分けている(`FrameSource` / `KeySource` / `Segmenter` / `Recognizer` / `LiveUi`)。**画面側は `LiveUi` と `KeySource` の別実装を足せば差し替えられる**。
- `live.rs` が `main.rs` の非公開関数に頼っているのは少数(`palm_rois`、`preprocess_for_palm_roi`、`extract_tag_features_impl`、`infer_frame_feature` など)。一方、画面出力と対話入力は `dialoguer` と `println!` に結びついている(live.rs に 40 箇所、main.rs に 99 箇所)。
- モデルのパスは作業ディレクトリ相対で固定(`models/*.onnx`、`../transformer_burn/models/...`、`../transformer_burn/data/raw_jsl`)。リポジトリ内の `pose_extractor/` から起動する前提で、アプリの同梱にはそのままでは使えない。
- 1フレームの特徴量は 126 次元(左右の手 21 点 × xyz、画像の幅・高さで正規化)で、`LiveFrame.feature` に入っている。**手の骨格の重ね描きは、この特徴量から追加の推論なしで描けるはず**(座標の正規化の向きは実装時に確認する)。
- カメラ入力は ffmpeg(別プロセス)。実機で、`-nostdin` と `-fps_mode passthrough` が必須と分かった(`live-demo-design.md` §8.4)。

### 3.2 エンジンと画面の会話(案Aの場合の提案)

エンジン側に、ターミナル表示の代わりに JSON を出す「ヘッドレスのライブ実行」を足す。これは `LiveUi`(出力)と `KeySource`(入力)の別実装にあたり、既存のループ(`run_session`)の流れは変えない。実装では、`run_session` の中に `preview`(縮小プレビューへ生フレームと特徴量を渡す)の呼び出し 1 行(`live.rs` 1402 行目)を足している(`LiveUi::preview` はデフォルト実装つきなので、ターミナル UI では何もしない)。

- ユーザー向け CLI の方針(フラグ無し・ウィザード優先、[[cli-interactive-wizard-preference]])とは別物として、**アプリ専用の内部入口**にする(利用者が直接叩くものではない)。入口の形は、メニューにもヘルプにも出さない隠し引数 `pose-extract --engine-json`(TTY 不要)として実装した(§3.2.1)。
- エンジン → 画面(標準出力、1行1メッセージ):
  - 起動完了と語彙一覧、状態(待機/記録中、手の有無、処理 fps、記録秒数)、認識結果(上位k件と確率、区間、自信なしの印)、メッセージ(短すぎる動きを無視、など)
  - プレビュー: 縮小した映像(例: 640×360、JPEG、最大10fps)と、手の骨格(126次元の特徴量そのもの)
- 画面 → エンジン(標準入力): 手動の開始/停止、モード切替(自動/手動)、終了
- 映像はエンジンが持つ(ffmpeg → エンジン)ので、画面側はカメラを開かない。**プレビューは認識とは別に縮小・符号化した複製**であり、認識に使う 1620×1080 の生フレームには手を入れない。

### 3.2.1 エンジン側の実装記録(2026-10-11、実装済み。カメラ実機は 2026-10-12 にユーザーが確認、§9.4 末尾)

実装は `pose_extractor/src/live/json_engine.rs`(`live.rs` の子モジュール)。`live.rs` 本体の変更は、`LiveUi` にデフォルト実装つきの `preview` メソッドを足して `run_session` がフレームごとに呼ぶ点と、`mod json_engine;` の宣言だけ。`main.rs` の差分は `--engine-json` の判定と分岐の数行。ターミナル UI の挙動は変わらない。**§3.2 の提案からの変更・追加は以下のとおりで、これ以外は仕様どおり**。

- 標準入力の最初の `start` で設定を受ける。`model_dir` 省略時は既定のデモ用モデル(作業ディレクトリ `pose_extractor/` 基準の相対パス。ONNX の `models/*.onnx` も同じ)。`preview` は省略 = 既定(max_fps=10, width=640)、`null` = プレビュー無し、`max_fps` は最大 30・`width` は 16〜4096 に丸める(丸めたら warn)
- `ready` に `preprocess` フィールドを追加(`"preprocess.json"` = モデルから / `"default"` = live_wizard と同じ既定)。`default` のときは info の `message` も出す。`vocab` は words.tsv の並びで、words.tsv に無いモデルのタグは末尾にタグ名のまま足す
- イベント `{"type":"segmenter","mode":"auto"|"manual"}` を追加(`set_segmenter` が実際に反映されたとき。記録中は反映を記録終了まで延期し、info の `message` で知らせる)
- 動画ファイル入力は、終端で `stopped` を出して終了する。「動画 + manual」は live_wizard と同じく再生開始と同時に録画を始め、終端で認識する。**start の直後に標準入力を閉じると quit 扱いで即終了するので、動画入力を手で試すときは入力を開けたままにする**(例は報告のコマンド)
- `status.fps` は入力のタイムスタンプ基準(カメラでは処理 fps、動画ファイルでは動画の fps)
- `status` は最大 10 回/秒(待機 ⇔ 記録中の変化は即時)。`preview` は縮小のみ推論ループ側で行い、JPEG 化・base64・書き出しは出力スレッドが担う。出力キューが詰まったら `status`/`preview` は捨てる(推論ループは止まらない)
- `preview.hands` の x,y は 0〜1 を少し外れることがある(クランプしない)。`left`/`right` は特徴量の左手枠/右手枠で、映像は反転していない。`crop` は ROI が人物追従・複数タイルのときは全体(0,0,1,1)
- 標準出力は JSON 行だけ。依存側の `println!`(モデル読み込み時の構成表示など)が混ざらないよう、起動時に fd 1 を標準エラーへ付け替え、元の標準出力は JSON 専用に複製して使う
- 終了: quit・標準入力 EOF・SIGTERM/SIGINT・標準出力の書き込み失敗のどれでも、カメラ用 ffmpeg を含めて後始末してから `stopped` を出して終了コード 0。回復不能な失敗は `error` を出して非 0。ループがカメラの 1 枚目を待っている最中でも止められるよう、監視スレッドが ffmpeg を強制終了する(`libc` クレートは足さず、`dup`/`dup2`/`fcntl`/`signal`/`kill` を `extern "C"` で宣言。`fcntl` は可変長引数の関数なので `...` 付きで宣言している)

実測(release、動画ファイル入力、実モデル `rec_demo_center_signspan`、2本・各7回の中央値、ready〜stopped の所要時間から算出した処理 fps): プレビュー無し 28.4 / 30.9、10fps・640px 27.4 / 29.8(-3.4% / -3.7%)、30fps・640px 26.0 / 28.4(-8.3% / -8.1%)。カメラ入力での負荷・発熱は未測定(§4)。

### 3.3 画面の内容(T1、提案)

- 大きなカメラプレビュー(**ユーザー回答(2026-10-11): 鏡のように表示する**。表示だけ左右反転し、認識に渡す映像は反転しない)
- 手が検出できる範囲(中央の正方形)の枠線。今回の実機で「手が近すぎると検出が落ちる」ことが分かったため、枠に収まる距離の目安になる
- 手の骨格の重ね描き(検出されているかが一目で分かる)
- 状態の表示(待機中 / 記録中 + 経過秒数)
- 認識結果: 日本語の語を大きく、確率つきの上位3件を棒グラフ。確信度が低いときは「自信なし」と明示
- 直近5件ほどの履歴、認識できる語(51語)の一覧
- 操作: スペースキーで手動の開始/停止、自動/手動の切替
- 見た目: コントラストと文字の大きさに配慮(ろう者が主な利用者になりうるため、視覚で全てが伝わること。音に頼らない)

## 4. 技術的な論点とリスク

| 論点 | 現状の見立て | 確度 |
|---|---|---|
| カメラの許可 | アプリ(.app)から起動するので、macOS のカメラ許可はアプリに紐づく。Tauri の Info.plist に `NSCameraUsageDescription` を書く方法がある(公式ドキュメントに記載)。**エンジン(子プロセスの ffmpeg)がカメラを開くとき、許可がアプリに帰属するか**は未検証 | 未検証。最初の試作で確かめる |
| 開発中の許可ダイアログ | 開発ビルドでは Info.plist が効かず許可ダイアログが出ない既知の報告がある(2021年の古いスレッド。現行版で再現するかは未確認) | 要確認 |
| ffmpeg の依存 | 今は Homebrew の ffmpeg を前提にしている。T1(このMacだけ)ならそのままでよい。配布(T3)では同梱するか、カメラ入力を ffmpeg なしにする必要がある。Homebrew 版は GPL ビルドで、同梱の可否はライセンスの確認が要る | T3 で判断 |
| ffmpeg の代替 | Rust のカメラクレート `nokhwa` の macOS 部分は、確認できた最新リリースが 2023年5月で、保守状況に懸念がある。`objc2` 系で AVFoundation を直接叩く道もあるが、調べきれていない | 未評価 |
| ブラウザ側のカメラ(`getUserMedia`)でカメラを開く案 | 1620×1080 の生フレームをプロセス間で運ぶ必要が出る(約5MB/枚)ほか、JPEG 化や自動画角調整で認識精度が学習データとずれる恐れがある。**認識経路には不採用**を推奨 | 推測 |
| ONNX Runtime の同梱 | 現在は `ort` の `download-binaries` でビルド時に取得している。.app に同梱するには、動的ライブラリを同梱して `ORT_DYLIB_PATH` で場所を指定する方式が使えそうだが、現行バージョン(2.0.0-rc.12)で未確認 | T3 で判断 |
| モデル・語彙ファイルの場所 | 現在は相対パス固定。アプリではリソースの場所を引数または環境変数で渡す形にする(T1 はリポジトリ内で起動するなら不要) | 実装時 |
| 発熱・負荷 | エンジン(約15fps)+ Web 画面の描画 + プレビュー符号化が同時に動く。MacBook Air M2 での負荷は未測定 | 試作で測る |
| `main.rs` との衝突 | 案Aなら `live.rs` の変更に閉じ、`main.rs` の差分は最小で済む | — |
| .app にしたときの PATH(推測) | Finder や Dock から起動した .app は、ターミナルの `PATH` を引き継がない。Homebrew の `/opt/homebrew/bin` が `PATH` に入らず、`ffmpeg` / `ffprobe` を名前で起動する現在の実装では spawn に失敗する見込み(未検証)。T1 のようにターミナルから起動する場合は `PATH` を引き継ぐので問題にならない。.app 化(T3 以降)のときに、ffmpeg の場所の指定方法を決める必要がある | 推測。.app 化で確認 |

## 5. 進め方の提案

12月までのデモを意識して、T1 を優先する。期間は目安で、撮影(12月)と並行する想定。

1. **スパイク(半日〜1日)**: Tauri の最小アプリで、(a) エンジンを子プロセスとして起動し JSON を受け取れるか、(b) 子プロセスの ffmpeg がカメラを開けて許可ダイアログが出るか(開発ビルドと .app の両方)、(c) 10fps 程度のプレビュー(JPEG)を表示して重さ(CPU・温度)が許容か、(d) 日本語が正しく描画されるか、を確かめる。**ここで案A/Bの最終判断をする**。
2. エンジン側: ヘッドレスのライブ実行(JSON 出力・プレビューの縮小符号化)を `live.rs` に足す。ユニットテストと、動画ファイル入力でのスモーク(カメラ無し)を付ける。
3. 画面側: §3.3 の T1 の画面を作る。
4. 仕上げ: .app としてビルド(未署名)し、友人に見せる想定の操作を通しで試す。
5. (任意)T2 の撮影モード。

ブランチは `feat/live-demo` を土台にして新ブランチを切る。Tauri のプロジェクトは `desktop/` のような新ディレクトリに置く案(Node の `node_modules` などの `.gitignore` を併せて整える)。

## 6. 検証方法

- エンジン: 既存のユニットテストと動画スモークの流儀。JSON の出力形式の固定テスト(各メッセージが決まった形で出る)を追加。
- 画面: 動画ファイル入力で、カメラ無しに通し確認できるようにする。
- 実機: カメラ許可、プレビューの滑らかさ、長時間動かしたときの発熱とメモリ、`q` や ×ボタンで終了したときにカメラ用 ffmpeg が残らないこと(CLI では Ctrl+C で孤児プロセスが残った。アプリの終了時には、子プロセスを確実に止める後始末が要る)。

## 9. GPUI を採用する場合の追記(2026-10-11)

### 9.1 調べて分かったこと(`cargo search` / `cargo info` とソースで確認済み)

- crates.io に `gpui` 0.2.2(Zed の GPU 描画 UI)がある。部品ライブラリ `gpui-component` 0.7.1(「GPUI Kit」の60以上のデスクトップ部品)もある。ほかに `gpui-macos-*`(macOS 向けの固定フォーク)など派生が多数あるが、どれが主流かは未確認。
- **既定ではビルド時に Metal シェーダのコンパイルが要る**: `gpui` の `build.rs` が `xcrun metal` を実行する(`build.rs` 196〜240 行付近)。この Mac は Command Line Tools のみの状態に見え(`xcode-select -p` = `/Library/Developer/CommandLineTools`、`xcrun -sdk macosx --find metal` が失敗、`/Applications/Xcode*.app` も見つからない)、そのままでは失敗する見込み。ただし**ユーザーは「Xcode は入れてあった気がする」と述べている(帰宅後に確認予定)**ので、入っているかどうかは未確定。
- **Xcode なしでも回避できる**: `gpui` には `runtime_shaders` 機能(`Cargo.toml` 54行目)があり、有効にするとシェーダをビルド時ではなく実行時にコンパイルする(`build.rs` 72〜74行目)。この場合は `xcrun metal` が不要になる。実行時のコンパイルのぶん起動がやや遅くなる可能性がある(未測定)。カメラは関係しない(カメラはエンジン側の別プロセスで扱う)。
- 1.0 前で版ごとに破壊的変更があるため、`Cargo.lock` で版を固定し、最初の動く版を記録する。

### 9.2 構成(変更点)

- 認識エンジンと画面の境界は §3.2 のまま(エンジンは別プロセスで、1行1メッセージの JSON)。GPUI は Rust なので、将来 1プロセス化(エンジンをライブラリにして画面から直接呼ぶ)もできるが、今回は境界を保つ。保つ理由は、Tauri へ戻す選択肢を残すことと、`main.rs` の大改造を避けること。
- エンジン側の作業(ヘッドレスのライブ実行)は GUI の種類に依存しないので、Xcode を待たずに進められる。

### 9.3 GPUI の試作(スパイク)で確かめること

1. ビルドが通る(Xcode の導入後)。最小のウィンドウが開く
2. 日本語が正しく表示される(フォントの扱い)
3. `gpui-component` の部品(ボタン、リスト、プログレスバー、テーマ)が使える。版の組み合わせ(`gpui` と `gpui-component` の対応)が合う
4. 画像を10〜15fps で差し替えて表示できる(エンジンからの JPEG を表示)。手の骨格と検出範囲の枠を、映像の上に重ね描きできる。鏡のように表示する(左右反転)
5. エンジンを子プロセスとして起動し、標準出力の JSON を受け取って画面を更新できる。アプリを閉じたときにエンジンとカメラ用 ffmpeg が残らない

→ ダメなら(特に 1〜4 のどれかで詰まる場合)Tauri に切り替える。切り替え判断の基準は、半日〜1日で動く画面が作れるかを目安にする(ユーザーの確認は未了)。

### 9.4 GPUI 試作の確認結果(2026-10-11、Xcode なし。事実の記録で、新しい決定ではない)

実装は `desktop/`(独立パッケージ `attention-app`、ワークスペースにはしない)。このMacは Command Line Tools のみで(`xcrun -sdk macosx --find metal` が失敗)、Xcode なしでビルド・起動できた。当時はカメラ実機とスクリーンショットでの目視が未確認だったが、2026-10-12 にユーザーが実機で操作して確認した(下記「実機での確認」)。

- **版の組み合わせ(§9.1 の記述との食い違い)**: `gpui-component` の最新 0.7.1 / 0.6.x は、`gpui` ではなく別名クレート **`gpui-pre` 0.3.x**(Zed のスナップショット)に依存し、そこには `runtime_shaders` 機能が無い。`gpui-component` **0.5.1 は `gpui ^0.2.2` に依存する**ので、`gpui = "=0.2.2"`(features = ["runtime_shaders"])と `gpui-component = "=0.5.1"` の組み合わせを使った。Cargo の feature 統合で、gpui-component が使う gpui にも `runtime_shaders` が効く。`Cargo.lock` で固定(`.gitignore` の `Cargo.lock` 無視を `desktop/` だけ打ち消した)。
- **1. ビルド・最小ウィンドウ**: `cargo build --release` が Xcode なしで通った(新規 cmake 等の追加ツールは不要)。依存を全部ビルドする初回は、debug 2分39秒 / release 4分57秒。ウィンドウは開き、エンジンからの映像・結果が画面状態に反映されることを確認(寸法ログでレイアウトを検証。実際の見た目はスクリーンショットが撮れず未確認)。
- **2. 日本語**: フォント `Hiragino Sans` を指定。実行時の診断で、代替フォントとは別のフォントとして解決でき、かな・漢字の字形があることを確認(描画結果の目視は未確認)。
- **3. gpui-component の部品**: Button(primary/danger/outline、選択状態)、Progress、Root、テーマ(ダーク)が 0.5.1 + gpui 0.2.2 で使えた。
- **4. 画像の差し替え・重ね描き・鏡像**: エンジンの JPEG(640×427)を読み取りスレッドでデコード→水平反転→手の骨格と検出範囲の枠を CPU で描き込み→`RenderImage`(BGRA)にして表示。実映像で骨格が手に重なること(x を 1-x にした鏡像が画像と一致すること)を、描き込み後の画像を目視して確認。表示は約 10fps(**動画入力でのエンジンのプレビュー間隔**。動画は最速で処理するので、プレビューの間引き 10fps が表示の上限になる)。**カメラ約 15fps では、このときの間引き(「前回通した時刻から 0.1 秒以上」)だと 1 枚おきになり、約 7.5 回/秒になる見込みだった**(0.067 秒間隔 → 0.067 秒後は不足、0.133 秒後に通る)。2026-10-11 のレビュー対応で間引きを「次に通してよい時刻を 1 間隔ずつ進める」方式に直した(下記「レビュー対応」)。修正後は、約 15fps の入力で 10 秒あたり 100 回(約 10 回/秒)、約 30fps・60fps でも 100 回になることを、合成の時刻列を使うユニットテストで確認した(旧方式の同じ入力での値は計算で 75 回)。カメラ実機での実測は未確認。
- **5. エンジンの子プロセス運用・後始末**: 動画入力で、ready → status → preview → result(こんにちは p=0.996)→ stopped → 終了コード 0 を確認。アプリの正常終了(終了処理の `Drop`)・SIGTERM・SIGKILL のいずれでも、エンジンと ffmpeg が残らないことを `pgrep` で確認(SIGTERM/SIGKILL はアプリ側で後始末できないが、パイプが閉じてエンジンが EOF で自分で後始末する)。カメラ経路の後始末は、偽の ffmpeg(寝るだけ)で確認した。実カメラでの動作は 2026-10-12 にユーザーが確認(下記「実機での確認」。終了後に ffmpeg が残らないかの記録は無い)。
- **6. カメラの許可**: 実装時点では未確認(カメラを開いていない)。2026-10-12 にユーザーがカメラ入力で動かせている(許可ダイアログの出方・ターミナル起動時の許可の帰属は記録なし)。
- **7. 負荷**: 動画入力・プレビュー 10fps で、アプリ本体は CPU 約 0〜5%・メモリ約 75〜80MB、エンジンは約 200%(動画は最速で処理するため。カメラでは約 15fps に律速される)、ffmpeg は 14〜43%。カメラ入力での負荷・発熱は未測定。

#### レビュー対応(2026-10-11、Opus のコードレビューの指摘を修正。事実の記録で、新しい決定ではない)

- **M1(JSON 用 fd が子プロセスに引き継がれる)**: `take_json_sink` が標準出力を `dup` した複製には close-on-exec(FD_CLOEXEC)が付かず、あとで起動するカメラ用 ffmpeg に GUI へつながるパイプの書き込み口が引き継がれていた。エンジンが後始末なしで死んでも、生き残った ffmpeg が書き込み口を握っているため、GUI に EOF が届かない。`dup` のあとに `fcntl(fd, F_SETFD, FD_CLOEXEC)` を付けるよう直した(定数値は macOS の `<sys/fcntl.h>` で確認: F_GETFD=1、F_SETFD=2、FD_CLOEXEC=1。`fcntl` は可変長引数なので `...` 付きで宣言)。偽 ffmpeg と `lsof` で、修正前は ffmpeg が fd 3 に JSON のパイプを持っていたのが、修正後は fd 0〜2 だけになることを確認した。偽 ffmpeg を残したままエンジンを `kill -9` しても読み手に EOF が届くことを、統合テストで固定した
- **M2(区切り方の選択が上書きされる)**: `start_camera` が開始前に選んだ「手動」を自動に上書きしていたのをやめ、選んだ値をそのまま `start` に送る。`start` の組み立てを `AppModel::start_command` に切り出してユニットテストを付けた
- **L1(終了要求の後でもカメラを開く)**: `build_real` が、カメラ(ffmpeg)を起動する直前に終了要求の旗を確認し、立っていれば開かずに `stopped` だけを出して終わる(動画入力も同様)。start と quit を続けて流しても、偽 ffmpeg が起動されないことを統合テストで確認
- **L2(GUI 経由で映像書き出しが有効になる)**: GUI がエンジンを起動するときに `LIVE_DEBUG_DUMP_DIR` を子に引き継がない(`env_remove`)。加えて、エンジンの JSON モードでこの環境変数が有効になった場合は、`message`(warn)でも画面に告知する
- **L3(約 15fps で間引きが 1 枚おきになる)**: 上記のとおり。長く止まったあとに溜まった分を連続して通さない(バーストしない)ことも、ユニットテストで固定した
- **L4(回収済み PID への kill の窓)**: `CameraSource::failure_reason` が ffmpeg を回収(wait)する直前に、PID の登録解除を呼ぶ処理(`before_reap`)を実行する。`live.rs` の変更は、フィールドと設定メソッドと 1 行の呼び出しだけ
- **L5(未知のイベント種別が警告になる)**: `type` が未知のイベントは `EngineEvent::Unknown`(`#[serde(other)]`)として読み、画面には出さず読み捨てる(標準エラーに 1 行出す)。壊れた JSON や `type` の無い行は従来どおり警告
- **L6(起動中・停止中の区切り方ボタン)**: 起動中・停止中は区切り方のボタンを無効にした。待機中(次の start に使う値を選ぶ)と認識中(エンジンへ切り替えを頼む)は押せる
- **テストの穴の補修**: 結果の数値が有限であることの検証を、`null` になっていないこと(serde_json は NaN を `null` にする)まで見る形に直した。GUI 側の偽エンジンテストは、送った `toggle` と `quit` がエンジンに届いたことを、受け取った行のファイルで確認する。SIGINT(Ctrl+C 相当)で終了する統合テストを SIGTERM と同じ流儀で追加した。あわせて、同じ動画を使う 2 本の統合テストが並列実行で互いの ffmpeg を孤児と見間違える既存の不安定さを、錠で直列化して直した
