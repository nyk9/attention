# デスクトップアプリでの撮影機能 設計案(提案・未決)

作成: 2026-10-12。**設計案であって決定ではない**。着手するか・いつやるかも未決。元になったのはユーザーのメモ(2026-10-12):
「学習データ作成の動画撮影を、デスクトップアプリでできるようにしたい。カメラプレビューに人の枠みたいなものを付けて『大体この辺にいてください』と示す。手指の認識ができているかをリアルタイムで見られると嬉しい」。

位置づけ: `docs/desktop-app-design.md` の **T2(撮影モード)**。同文書 §7 で「T2 は今回の範囲外」とされていたので、これはその範囲を広げる提案にあたる。**範囲を広げるかどうかはユーザー判断**。

## 1. 目的と、解きたい問題

今の撮影は OBS/QuickTime で録画し、`pose-extract` の撮影セッションが保存先を監視して取り込む方式。困りごと(CLAUDE.md の記録と実撮影の経緯から):

- 手が検出できたか(`ng_hands`)は**撮った後にしか**分からない。一人撮影で、撮り直しのコストが高い
- 立ち位置・画角が撮影日ごとにずれる(stage1 と stage2 で手の外側への伸びの最適オフセットが符号まで反転した、という実測がある)。CenterSquare の ROI は余裕がほぼ無く(手の 3.7% が切れる)、画角のずれが直接効く
- 一人撮影のため録画の前後に手を下げた時間が長い(検出区間は動画の半分弱)。開始・終了の操作ラグが質を落とす
- 次に何の語を何本目で撮るかを、別画面の進捗表示で確認している

## 2. 既にあって、そのまま使えるもの(コードで確認済み)

| 部品 | 場所 | 使い道 |
|---|---|---|
| カメラ入力(ffmpeg avfoundation、1920x1080 を 1620 幅に中央クロップ) | `pose_extractor/src/live.rs` の `CameraSource` | 既存の撮影データ(1620x1080、30fps、h264 約 7.7Mbps)と同じ画角で撮れる |
| 手の骨格・検出範囲(CenterSquare 枠)のリアルタイム重ね描き | `desktop/src/overlay.rs`、エンジンの `preview` イベント | 「手指の認識ができているか」の要望の大部分は、**既にライブ認識画面にある** |
| 鏡像表示(表示のみ反転、保存は反転しない) | `desktop/` | そのまま |
| 語リスト・撮影数の集計・次の語の選択 | `progress.rs`(`load_words` / `merge_index` / `next_word`) | お題の表示に使える |
| 取り込み(命名 `<word_id>_<romaji>/<rep>.mp4`、`index.tsv` 記帳) | `progress.rs` の `ingest` | 保存後の記帳をそのまま使える |
| 手検出の合否判定(連続して検出できた最長区間 1.0 秒以上) | `progress.rs` の `HandChecker` / `MIN_HAND_RUN_SECONDS` | 撮影直後の合否表示に使える |
| 人物の肩位置(153 テイク分) | 今回作った `body_sequence`(`pose_dict_full_center_body.json`、gitignore 対象) | 立ち位置ガイドの基準位置を、実データの中央値から決められる |

つまり**新規に作る必要があるのは、(a)アプリ内録画、(b)立ち位置ガイドの描画、(c)お題・合否の画面、の 3 つ**。

## 3. 守るべき境界(ユーザー明示の制約、desktop-app-design.md §1 から)

- ライブ認識の経路は映像・特徴量を保存しない
- 撮影モードは**別モード**。書き込みはそのモードの間だけ、画面に録画中であることを常に明示する
- **モード間で書き込み経路のコードを共有しない**

設計への含意: 録画・保存は `capture` という別モジュール(エンジン側 `pose_extractor/src/live/capture.rs` を新設)に閉じる。ライブ認識のコードから `capture` を呼ばない。テストで「ライブ認識モードでは `raw_jsl` にも一時領域にもファイルが 1 つも増えない」を固定する(§7)。

## 4. 構成の提案

### 4.1 カメラは 1 本だけ開き、エンジンが録画も担う(推奨)

案:
- **案1(推奨): エンジンが 1 本の ffmpeg で受けた生フレームを、(a)認識/プレビュー用と、(b)録画用エンコーダ(別の ffmpeg、stdin に生フレーム)の両方に流す。** カメラを二重に開かない。録画の画質を既存データ(1620x1080・30fps・h264)に揃えられる
- 案2: アプリ(GUI)側が別に ffmpeg でカメラを開いて録画する。**macOS のカメラを 2 プロセスが同時に開けるか、フレームレート・形式が競合しないかは未検証**で、プレビュー(エンジン)と録画(GUI)で映像がずれる懸念もある。不採用を推奨

案1 の注意点(未検証):
- 録画用エンコーダが重くなると認識・プレビューが遅れる。撮影モードでは**認識(語の推論)は止めて、手検出(骨格表示と合否)だけ動かす**のが現実的。負荷は撮影モード専用に測る
- 生フレームを 2 箇所へ流す分の CPU/メモリ。1620x1080x3 バイト x 30fps は約 150MB/秒で、パイプ 1 本ぶんは既に支払っている。エンコーダへの追加ぶんの実測が要る
- 録画の画質設定: 既存データは約 7.7Mbps の h264。同じ設定に揃えるか、より高画質(crf を下げる)にするか。**エンコード設定が違うと手検出に微妙に効く可能性がある**が、測っていない(未確定)

### 4.2 エンジンとの会話(追加分の提案)

`--engine-json` の既存プロトコルに足す。ライブの `start` とは**別のモード指定**にする。

- 画面 → エンジン: `start` に `mode: "capture"`(お題の語 ID・テイク番号を渡す)/ `capture_record`(録画開始)/ `capture_stop` / `capture_accept`(採用)/ `capture_discard`(破棄)
- エンジン → 画面: `capture_state`(待機・カウントダウン・録画中・判定中)/ `capture_saved`(保存先、長さ、手検出の最長連続区間の秒数、合否の見立て)
- 録画中は一時領域(例: リポジトリ外の作業用ディレクトリ)に書き、**採用したときだけ** `raw_jsl/<word_id>_<romaji>/<rep>.mp4` へ移して `index.tsv` に記帳する。破棄なら一時ファイルを消すだけ。`raw_jsl` を汚さない

### 4.3 立ち位置ガイド

- 表示: プレビュー(鏡像)の上に、頭と肩の輪郭の半透明の枠を重ねる。枠の位置と大きさは、既存 153 テイクの肩中心・肩幅の**中央値**から決める(`body_sequence` から計算。動かない定数でよい)
- 目的は「だいたいこの辺」。**厳密さは不要**(実験の結果、肩基準にしても認識精度は変わらなかったので、位置の揃えは精度のためではなく、**手が CenterSquare 範囲に収まる確率を保つため**)
- 提案: 最初は静的な枠のみ。**リアルタイムで人物を検出して「ずれています」と出す機能は後回し**(人物検出+BlazePose を毎フレーム/数 fps で回す分の負荷が要る。必要になったら追加)
- 手が検出範囲(CenterSquare の枠)からはみ出しそうなときの警告は、骨格が既に出ているので、**手の点が枠の縁に近づいたら枠を赤くする**程度で足りる見込み(方向・指示語で手が切れやすいという実測に直接効く)

### 4.4 リアルタイムの手指認識表示

既に実装済みの骨格・枠の重ね描きをそのまま使う。撮影モード用の追加は次の 3 つ:

- 左右どちらの手が今検出されているか(`status.hands` の L/R/LR)を大きく表示
- 「連続して手が検出できている秒数」を実行中に表示し、合格ライン(1.0 秒)を超えたら色を変える(撮影後の判定と同じ基準を、撮影中に見せる)
- 録画中に手が一度も検出されていないときの警告

### 4.5 お題の表示と記帳

- 画面に「次の語: こんにちは(001)、3 本目 / 目標 10」を大きく出す。語リストと進捗は `words.tsv` と `index.tsv` から読む(`progress.rs` の関数を呼ぶ)
- 取り込みは `ingest` をそのまま使う(命名・`index.tsv` 記帳・合否の記録)。撮影モード専用の書き込み経路にしたいので、`ingest` 本体を共有する場合は**撮影モード側からの呼び出しだけ**にし、ライブ認識側からは到達できないことをテストで確認する
- 使用手(左手を約 10% 含める方針)の案内を出すかは**未決**(現状は撮影者の判断。画面が「今回は左手で」と指示する機能は、方針の運用を変えるのでユーザー判断)

### 4.6 録画の開始・終了

一人撮影のラグ対策として、次を提案する(どれも未決):

- **カウントダウン開始**: 開始キーを押して 3 秒後に録画開始(席に戻る時間)
- **自動終了**: 手が下がり、検出が一定時間(例 2 秒)途切れたら自動で録画を止める。これで後ろの手ぶら時間が減る
- 手動の開始/終了も残す
- 長さの目安(`DURATION_MIN_MS`=2 秒、`DURATION_MAX_MS`=10 秒)を超えたら警告

## 5. 段階の提案

各段階だけで使えるようにして、途中で止めてもよい形にする。

| 段階 | 内容 | 書き込み | 規模の見込み |
|---|---|---|---|
| R0 | 撮影用の画面: 立ち位置ガイド枠、手の連続検出秒数と L/R の表示、お題と進捗の表示(読み取りのみ)。**録画はしない**。今までどおり OBS/QuickTime で撮る | なし(`index.tsv` も読むだけ) | 小。ライブ認識画面の流用が中心 |
| R1 | アプリ内録画: エンジン側 `capture` モジュール、一時領域への録画、採用で `raw_jsl` へ取り込み。撮影直後の合否表示 | 採用時のみ | 中。ffmpeg の 2 本目、負荷測定、境界のテストが要る |
| R2 | カウントダウン・自動終了・撮り直しの操作性 | 同上 | 小〜中 |

**R0 から始めるのを推奨**(撮影中の今日からでも、OBS と併用できる)。R0 は何も保存しないので、データの境界に触れない。

## 6. 技術的な論点とリスク

| 論点 | 見立て | 確度 |
|---|---|---|
| 認識を止めて手検出だけにする場合の負荷 | 手検出のみなら現行ライブ(約 15fps)より軽い見込みだが、エンコーダ追加ぶんを含めた実測は無い | 未検証 |
| カメラの fps | 既存データは 30fps。ライブ認識は約 15fps(CAMERA_FPS)。**撮影モードで 30fps を取れるか**が未確認 | 未検証。最初に確かめる |
| 画角の一致 | ライブ用の入力は 1920x1080 を 1620 幅に中央クロップ(既存データと同じ 1620x1080)。ただし**既存データが実際にどのカメラ・設定で撮られたかは記録が無い**(OBS/QuickTime、外付けか内蔵か) | 同じカメラかどうかの確認をユーザーに聞きたい |
| 画質差による認識への影響 | アプリ内録画と OBS 録画で、エンコード設定が違う動画が混ざる。手検出・手形記述子への影響は測っていない | 未検証。混ぜる前に、同じ語で両方撮って dict を作り比較するのが安全 |
| `ingest` の再利用 | `progress.rs` の `ingest` は非公開関数。`pub(crate)` にするか、取り込み専用の関数を切り出す必要がある | コードで確認 |
| 録画中の操作 | 一人撮影ではキーボード操作が難しい場合がある。フットスイッチ等は不要としても、**手の動き(例: 両手を一度大きく上げる)で開始する**案もある | 未検討 |
| 同意書との関係 | 協力者が撮影に使う場合、アプリ内で同意の確認が要る可能性がある(`nft` リポジトリ側の議論)。**現在のデータはすべて開発者本人** | 協力者が現れたときの別論点。今回は扱わない |

## 7. 検証方法

- エンジン: 偽の ffmpeg を使った統合テストの流儀(既存)。`capture_*` イベントの形を固定する golden テスト
- **境界のテスト**: ライブ認識モードで start→quit を流しても、`raw_jsl` と一時領域にファイルが増えない。撮影モードで破棄したとき、一時ファイルが残らない
- 実機: カメラ 30fps で録画した動画が既存データと同じ解像度・fps になること。録画中の発熱と、認識停止時の CPU。終了後に ffmpeg が残らないこと(既存の確認項目)
- 取り込みの往復: アプリで撮った 1 本を `build-dict` に通して手ポーズ列が出ること

## 8. 未決(ユーザーの判断待ち。矢印は私の推奨で、決定ではない)

1. **範囲を広げるか**: desktop-app-design.md §7 の「T2 は範囲外」を変更してよいか → R0 だけ先に、R1 以降は撮影の手間の実感を見てから
2. **既存データのカメラ**: 既存の `raw_jsl` は何で撮ったか(内蔵 FaceTime か外付けか、OBS か QuickTime か)。画角を揃える基準になる → 教えてもらえれば R0 のガイド位置の検証に使う
3. **撮影モードで認識を止めるか**: 負荷と、データの境界(撮影中にライブ認識を動かさない)の両面から → 止める
4. **録画の画質**: 既存に揃える(約 7.7Mbps)か、高画質にするか → 既存に揃え、混在の影響は先に測る
5. **使用手の案内**: 画面が「今回は左手で」と示すか → 示さない(現行の運用を変えない)
6. **自動終了・カウントダウン**: 入れるか、秒数 → R2 で、実際に使いながら決める
7. **立ち位置ガイド**: 静的な枠のみか、リアルタイム検出でずれを知らせるか → 静的のみ
8. **ブランチ**: ルールは `feature/`。新規は `feature/desktop-capture` を `feat/desktop-app` の履歴から切る案(`feat/desktop-app` は PR #16 でマージ済み)

## 9. R0 実装記録(2026-10-12、ブランチ `feature/desktop-capture`。事実の記録で、新しい決定ではない)

R0(撮影ガイド。録画なし・書き込みなし)を `desktop/` に実装した。§8 の未決のうち 1(範囲)はユーザーの指示で R0 だけ着手、7(立ち位置ガイド)は静的な枠のみで実装した。他の未決はそのまま。

### 9.1 実装した内容

- **モード切替**: ライブ認識画面の操作欄に「モード: ライブ認識 / 撮影ガイド」のボタンを追加(停止中のみ切り替え可)。撮影ガイドでは右列が「次の語・手の検出・検出範囲・凡例」に変わる。ライブ認識の右列・操作・挙動は従来どおり
- **エンジンの使い方**: 撮影ガイドでは `start` を区切り方「手動」で送り、開始操作(`toggle`)は送らない(ボタンを出さず、スペースキーも無視)。`result` イベントが来ても表示しない(動画入力 + 手動ではエンジンが再生開始と同時に記録して終端で認識するため、来ることがある)。ライブ認識で選んでいた区切り方は、撮影ガイドの `ready`/`segmenter` で上書きしない。**pose_extractor のコードとエンジンの JSON 仕様は変更していない**
- **立ち位置ガイド**(`desktop/src/capture_guide/silhouette.rs`): 鏡像プレビューに、頭(楕円)と首・肩・腕の輪郭を白の半透明(不透明度 0.6)で描く。位置と大きさは下の定数(データの中央値)から決め、頭の大きさ・首肩の形の係数は目視で調整した目安(データ由来ではない)
- **手の検出**(`hand_run.rs`): `status.hands` を大きく「左手 / 右手 / 両手 / 手なし」で表示。左右別々に「連続して検出できている秒数」を数え、良い方を表示。1.0 秒以上で緑(未満は琥珀色)、色だけに頼らないよう「合格ライン以上 / 1.0 秒未満」の文字も出す。途切れたら「直前の連続区間: X 秒」も出す
- **縁の警告**(`edge.rs`): 手の点が検出範囲(`preview.crop`)の縁から枠の幅・高さの 3%(`EDGE_MARGIN_RATIO`)以内、または枠の外にあれば、枠を赤く太く(黄・2px → 赤・5px)し、「検出範囲の右の縁に手が近づいています。枠の内側へ」のように、画面に見えている向き(鏡像)で知らせる
- **お題と進捗**(`progress.rs`): 「次の語」を大きく(例: `かれ(011)` と `4 本目 / 目標 10`)、全体の本数・完了語数を小さく表示。3 秒ごとに読み直す(撮影中に他のツールが動画や index.tsv を足すため)。読めないときは赤い枠に日本語の理由を出し、他の機能は動かす
- **データの場所**: 環境変数 `ATTENTION_DATA_DIR`、無ければ `<リポジトリ>/transformer_burn/data/raw_jsl`(リポジトリの場所は既存の `ATTENTION_ROOT` の解決と同じ)
  - **worktree 対応(後日修正)**: raw_jsl は gitignore 対象で worktree には複製されないため、既定の場所が無いときは `git rev-parse --git-common-dir`(読み取り系のみ)から本体チェックアウトを探し、その raw_jsl を使う。`ATTENTION_DATA_DIR` 指定時は従来どおり最優先でフォールバックしない。git の呼び出しは「書き込み・プロセス起動 API 禁止」の検査対象外の `engine.rs` に置き、決定ロジックは純関数 `choose_data_dir`(`progress.rs`)に分離してテスト
  - 読めないときの表示に「決め方(環境変数 / 既定の場所 / 本体へのフォールバック)」と探した場所、「worktree では raw_jsl は複製されません。本体のパスを ATTENTION_DATA_DIR に指定してください」を併記
- **開発・検証用の環境変数**: `ATTENTION_APP_MODE=capture-guide` で撮影ガイドから起動。`ATTENTION_APP_DEBUG` 有効時、撮影ガイドの表示内容(手・秒数・合格判定・直前・縁・お題)を変化時に標準エラーへ 1 行出す

### 9.2 規則の出典と、progress.rs との違い

- 合格ライン 1.0 秒・瞬断 1 サンプルの橋渡し・左右の良い方で判定 = `pose_extractor/src/progress.rs` の `MIN_HAND_RUN_SECONDS` / `MAX_RUN_GAP_SAMPLES` / `ingest`。ただし近似で、厳密には一致しない:
  - 秒数の数え方: progress.rs は「検出サンプル数 / サンプル毎秒」、ここは「区間の最初の検出時刻〜最後の検出時刻」(差はおおむね 1 サンプル間隔)
  - 1 サンプルの長さ: エンジンの status は最大 10 回/秒なので瞬断の許容は約 0.1 秒。progress.rs(約 3 サンプル/秒)では約 0.33 秒
- **経過時間は「読み取りスレッドが status 行を受け取った時刻」**。status/preview の JSON に時刻が無く、`rec_secs` は記録しない撮影ガイドでは 0 のまま使えないため。UI が Inbox を見る時刻にしなかったのは、Inbox の status が最新 1 件だけを残す作りで途中のサンプルが消えるため(サンプルは別キューに全件積む)。カメラでは受信時刻がカメラの時刻とほぼ一定の遅れで進む見込み(実カメラでは未確認)。動画入力ではエンジンが最速で処理するので動画の時刻とは一致しない
- 次の語 = progress.rs の `load_words` / `scan_takes` + `merge_index` / `take_counts` / `next_word` と同じ規則を `desktop` 側に再実装(pose_extractor への依存は足していない)。ファイルが正で、index.tsv は quality_flag を引くためだけに使う。`ng` で始まる quality_flag は数えない。セッションの「スキップ」は無い。**progress.rs と違い、words.tsv が無くてもテンプレートを書き出さない**(読めない理由を表示する)

### 10.1 実装した内容

- **エンジン側**(`pose_extractor/src/live/capture.rs` を新設、`json_engine.rs` に会話の定義を追加)
  - `start` の `mode: "capture"` と `data_dir`(登録先。**絶対パスのみ**、フォルダで `words.tsv` が読めること)、`countdown_secs`(省略 = 3 秒、0〜10)。満たさなければカメラを開く前に `error` で終わり、何も作らない
  - 認識モデルは読み込まず、手検出(Palm + Hand、中央正方クロップ)とプレビューだけ動かす。語の推論はしない
  - **録画**: カメラ用 ffmpeg は 1 本。読み取りスレッドが受けた全フレームを、(a)従来どおり最新フレーム置き場(手検出・プレビュー)と、(b)録画中だけ、録画用の別 ffmpeg(stdin に rawvideo rgb24 → libx264 `-preset veryfast -profile:v high -pix_fmt yuv420p -b:v 7700k -maxrate 9600k -bufsize 15400k`、音声なし、一定フレームレート)へ流す。録画先は `std::env::temp_dir()/attention-capture-<pid>/take-N.mp4`(リポジトリの外)
  - **カウントダウン**(既定 3 秒)→ 録画 → 手動停止。最長は「コマ数 ÷ fps が必ず 10 秒未満」になるコマ数(30fps なら 299 コマ = 9.97 秒)で自動停止し、注意を出す(ちょうど 10.0 秒だと長さの評価で `長すぎる` に当たるため 1 コマ引いてある)
  - **判定**(別スレッド): `progress.rs` の `HandChecker` をそのまま使い(毎秒約 3 サンプル、連続して手が検出できた最長区間、瞬断 1 サンプルまで橋渡し、1.0 秒以上)、長さは `DURATION_MIN_MS`(2 秒)〜`DURATION_MAX_MS`(10 秒)で評価。判定用のモデルは録画の前(起動時)から別スレッドで読み込む
  - **採用**: `read_words` / `scan_takes` / `load_index` / `merge_index` / `next_rep_idx` / `new_take_row` / `stage_index` で `raw_jsl/<word_id>_<romaji>/<NN>.mp4` へ移し、`index.tsv` に 1 行足す。順序は「新しい index を一時ファイルに書く → 動画を移す → 一時 index を `rename` で置き換える」で、動画を移せなければ index は変えず、index の置き換えに失敗したら動画を一時領域へ戻す。`<NN>.mp4` が既にあれば上書きせず番号を進める
  - **破棄**: 一時ファイルを消すだけ。録画中・カウントダウン中・判定済みで可(判定中は、判定の ffmpeg が読んでいるので判定が終わってから)。「撮り直し」は画面が破棄 → 録画開始を続けて送る
  - 終了(quit・EOF・SIGTERM)では録画を止めて捨て、判定の終わりを待ち、一時領域を消し、カメラ用 ffmpeg を止めてから `stopped`。強制終了で残った一時フォルダは、次の起動時に持ち主の PID が死んでいることを確かめて掃除する(`take-*.mp4` だけ消し、ほかのファイルがあればフォルダは残す)
- **プロトコル**(§4.2 の案どおり): 画面 → エンジン `capture_record`(`word_id` 付き)/ `capture_stop` / `capture_accept`(`confirm_ng`)/ `capture_discard`。エンジン → 画面 `capture_state`(`phase` = idle / countdown / recording / judging / judged、秒数、fps、コマ落ち、語と見込みのテイク番号、**登録先 `data_dir`**、判定、注意)/ `capture_saved`(登録先の相対・絶対パス、番号、`quality_flag`、判定、長さ)。golden テストは両側に追加(`json_engine.rs` の `golden_capture_state` / `golden_capture_saved` / `parse_capture_commands_and_start_mode`、`desktop/src/protocol.rs` の `parse_capture_state_and_saved` / `capture_command_lines`)。未知のイベントは従来どおり `Unknown` で読み捨て
- **画面側**(`desktop/`)
  - **モードを 3 つにした**: ライブ認識 / 撮影ガイド(録画なし。R0 のまま) / **撮影(録画あり)**。「撮影(録画あり)」だけが `mode: "capture"` で書き込みうるエンジンを起動する。立ち位置枠・手の連続秒数・縁の警告・お題は撮影ガイドと共通
  - 右列の先頭に操作パネル(`render_capture_panel`): 状態の見出し、判定の 1 文(エンジンが組み立てた文)と数字、ボタン(段階に応じて 録画開始 / 取り消し / 停止・録画を捨てる / 採用して登録・NG として記録・撮り直し・破棄)、登録先のパスと決まり方、注意、直近の登録結果
  - **録画中の明示**: 映像の上の「● 録画中 X.X 秒」、プレビューの下の状態表示の「● 録画中」、パネルの見出しの 3 か所に常に文字で出す。カウントダウンは映像の上に大きな数字(180px)。色だけに頼らず文字でも示す(「使えそう」「使えない」「● 録画中」など)
  - スペースキー: 待機中 = 録画開始、カウントダウン/録画中 = 停止(取り消し)、**判定中・判定済みでは何もしない**(うっかり採用や撮り直しにならないように)
  - 録画する語は**画面が出している「次の語」**(`capture_record` に `word_id` を付けて送る。エンジンはその語として録画する)。お題が読めていなければ録画開始を無効にする。登録できたら、お題・本数をすぐ読み直す(3 秒ごとの読み直しを待たない)

- **開発・検証用**: `ATTENTION_APP_MODE=capture`(撮影(録画あり)から始める)、`ATTENTION_APP_CAPTURE_SCRIPT="record:6,stop:13,accept:32"`(起動からの秒数でボタン操作を自動実行。実際のボタンと同じメソッドを通る)

### 10.2 規則の出典と、progress.rs の撮影セッションとの違い

- 判定の規則(1.0 秒・瞬断 1 サンプル・毎秒約 3 サンプル・左右の良い方)と長さの範囲は、撮影セッションの取り込みと**同じ関数・同じ定数**を使っている(コピーしていない)。取り込みの規則も同様。そのために `progress.rs` を次のとおり変えた(撮影セッションの挙動は変えていない)
  - `write_index` を `stage_index` + `commit` に分けた。**撮影セッションの `index.tsv` 書き込みも一時ファイル経由のアトミックな置き換えになった**(ユニットテスト `write_index_is_atomic_via_a_temp_file`)
  - `load_words` から、書き出さずに読むだけの `read_words` を分離(撮影モードは、`words.tsv` が無いときにテンプレートを書き出す `load_words` を使えない)
  - `ingest` から `take_dir_name` / `take_file_name` / `quality_flag_for_run` / `new_take_row` / `now_recorded_at` を切り出し、`scanned_next_rep`(ffprobe を呼ばないテイク番号)を追加。いくつかの関数・定数を `pub(crate)` にした
- **違い 1(長さの扱い)**: 撮影セッションは、長さが範囲外でも**注意を出すだけ**で quality_flag は `ok`(手が足りなければ `ng_hands`)。撮影モードは指示に従い、長さが範囲外なら「使えない」とし、手は足りていて長さだけ範囲外のテイクには **`ng_duration`**(新しい値。`ng` で始まるので、目標数にも build-dict 用エクスポートにも数えられない)を付ける。手も足りないときは `ng_hands`。判定そのものができなかったときは、撮影セッションの手検出チェック失敗と同じく quality_flag は空
- **違い 2(判定の対象)**: 撮影セッションは取り込み後の `raw_jsl` 内のファイルを判定する。撮影モードは一時領域の録画を判定し、採用したものだけを移す
- **違い 3(ng の扱い)は同じ**: 使えないテイクも、ユーザーが明示して採用すれば `ng_*` 付きで記帳し、番号は進み、目標数には数えない(撮影セッションが ng のテイクも記帳して番号を進めるのと同じ)。ただし撮影モードでは、画面のボタンが「NG として記録(登録名)」と書かれ、エンジンも `confirm_ng: true` が無いと断る(確認なしでは記録しない)

### 10.3 録画の fps・画質・コマ落ちの挙動

- **カメラの要求は元から 30fps**(`CAMERA_FPS` = 30)。「約 15fps」は**手検出の処理速度**で、カメラの到着間隔ではない。ライブ認識は最新の 1 枚だけを見て古いコマを捨てるが、撮影モードの録画は読み取りスレッドが受けた**全フレーム**を流すので、手検出が遅くても録画には影響しない
- **録画の fps は、実測から決める**(`decide_record_fps`): カウントダウン中(録画の前)のフレーム到着間隔の**中央値**から実測する(起動直後の 1 秒は除く)。28.5〜31.5 fps は 30 とみなす。それより遅ければ**実測値をそのまま宣言し**(フレームは複製しない)、画面に警告を出す。測れなかったときは 30 とし、警告を出す。平均でなく中央値にしたのは、動画ファイル入力の検証で、処理が詰まったあとの追い付きの一気読みで平均が 33〜35 fps に振れ、録画の再生が速くなる不具合に当たったため
- **録画のキューが詰まった場合**(24 コマ = 約 125MB): そのコマは**複製せず捨てて数え**、画面に「コマ落ち N 枚(動きが少し速く記録されます)」を出し、判定の文にも添える。使えないにはしない
- **録画中に実際に届いたコマの平均 fps**を最初と最後のコマの到着時刻から測り、動画に宣言した fps と 5% 以上ずれていたら画面に注意を出す(`fps_mismatch_note`)
- **画質**: 既存の raw_jsl の動画(`001_konnichiwa/02.mp4`: h264 High / 1620x1080 / yuv420p / 30fps / 7.69Mbps)に揃えた。エンコード設定は ABR 7700k。動画ファイル入力での実測: h264 High・1620x1080・`r_frame_rate` 30/1・yuv420p・**7.2〜7.3Mbps**。録画用エンコーダ単体(復号込み)の速さは 126 コマ 2.32 秒(約 54fps = 実時間の約 1.8 倍)で、ビットレート 7.73Mbps(この Mac で。カメラ・発熱込みでは未測定)

### 10.6 設計案からの変更点

- §4.2 の「`start` に `mode: "capture"`(お題の語 ID・テイク番号を渡す)」→ お題の語は `start` ではなく**録画開始のたびに `capture_record` で渡す**(1 回の起動で何本も撮るため)。テイク番号は渡さず、エンジンが採用の瞬間に決める(`capture_state.word.rep_idx` は見込み)
- §4.2 の `capture_saved`(判定を含む)→ **判定は `capture_state`(phase = judged)で先に画面へ渡し**、`capture_saved` は採用して登録した結果だけにした
- 指示の「撮影ガイドモードの右列に足す」→ **3 つ目のモード「撮影(録画あり)」を作り、撮影ガイド(録画なし)は R0 のまま**にした。理由: 撮影ガイドが「録画も保存もしない」という R0 の保証をそのまま保てること、書き込みうるエンジンを起動するモードが画面上で区別できること。ユーザーが「ガイドと録画を 1 つのモードにしたい」なら、画面側の切り替えだけの変更で済む
- 長さが範囲外のテイクの quality_flag に **`ng_duration`**(新しい値)を導入した(10.2)
- 録画の fps は、指示の「実際のフレーム間隔から決める」を、平均でなく**中央値**にした(10.3)
- `capture_guide_tests.rs` の検査対象を、`capture_guide/` だけから、画面側の `capture_rec.rs` / `state.rs` / `protocol.rs` にも広げた。禁止リストは変えていない。理由: R0 の意図(表示のコードから書き込み API を呼ばない)は R1 でも保ち、録画に関わる画面側のソースにも同じ制約をかけるため。`main.rs` と `engine.rs` はエンジンの子プロセスを起動する(`Command::new`)ので対象外
- 登録先 `data_dir` は**絶対パスのみ**(相対パスは、画面とエンジンで作業フォルダが違い、別の場所を指すため)。画面は絶対パスにして送る

### 10.7 ユーザー判断が要る点(推奨は添えるが、決定ではない)

1. **録画の fps・画質**: 30fps・約 7.7Mbps で既存に揃えた。カメラが 30fps を出せない場合は実測 fps で録画して警告する。この「実測 fps で書いた動画をデータに混ぜてよいか」(動きの速さの扱いが既存と変わる)は撮影してから判断 → 警告が出たテイクは撮り直す
2. **ng のテイクの扱い**: 使えないテイクも、明示して採用すれば `ng_*` 付きで記帳し、番号は進む(撮影セッションと同じ)。「使えない」は採用不可にもできる(番号が進まず、再撮影の跡も残らない) → 現状のままだと、撮影セッションと同じく ng の跡が `index.tsv` に残る。`ng_duration` を新設したことの可否(長さが範囲外でも `ok` にして注意だけ、という撮影セッションと同じ扱いに戻す案もある)
3. **書き込み先の安全策**: 画面は登録先のパスと決まり方(環境変数 / 既定の場所 / 本体へのフォールバック)を**常に表示**し、既定の場所・フォールバックのときは「撮影済みの本物のデータに書き込みます」と明示する。採用ボタンに登録名(`011_kare/04.mp4`)を書く。エンジンは、登録先が存在せず `words.tsv` も読めないときは録画させず、フォルダを作らない。**ただし、本物のデータに書き込む採用の前に確認ダイアログは出していない**(押したらすぐ登録)。本物に初めて書き込む前だけ確認を挟む案、または最初は `ATTENTION_DATA_DIR` を試験用の場所にして試す運用 → 実カメラで試すときは後者を推奨
4. 撮影(録画あり)で右列の縦の並び: 撮影中に見たい「手の検出」「次の語」と操作パネルのどれを上に置くか(見た目を確認できていないため未調整)
5. 使用手の案内、自動終了、立ち位置ガイドの方式は R0 / R2 の未決のまま(今回は触れていない)

### 10.8 ユーザーが実カメラで試す手順

1. エンジンとアプリをビルド: `cd pose_extractor && cargo build --release`、`cd ../desktop && cargo build --release`(この worktree のモデルは MAIN からのシンボリックリンク。MAIN で実行するなら不要)
2. **最初は試験用の登録先で試す**: `mkdir -p /tmp/rec_try/raw_jsl && cp transformer_burn/data/raw_jsl/words.tsv /tmp/rec_try/raw_jsl/`(`index.tsv` は無くてよい。本物の `raw_jsl` は触らない)
3. `cd desktop && ATTENTION_DATA_DIR=/tmp/rec_try/raw_jsl ATTENTION_APP_MODE=capture ./target/release/attention-app`(Photo Booth など、カメラを使う他のアプリは閉じておく。カメラの許可ダイアログが出たら許可)
4. 「カメラで開始」→ 映像と骨格が出て、右列の先頭に「待機中(録画していません)」と「登録先: /tmp/rec_try/raw_jsl」が出ることを確認(登録先の下の注意は、環境変数での指定なので「テスト用の場所でなければ…」と出る)
5. **見るところ**:
   - 録画を始めると、右列に「録画の fps: 30.0 fps」と出る(測った fps が 28.5〜31.5 なら 30 と出る)。**30 に近くなければ注意が出る**(カメラの設定・負荷を疑う)
   - 「録画開始(スペース)」→ 映像の上に大きなカウントダウン(3, 2, 1)→「● 録画中」が映像の上・左下・パネルに出る → 「停止」(またはスペース)
   - 停止から数秒で「使えそう」または「使えない」と、理由・最長連続秒数・長さが出る
   - 「採用して登録(011_kare/01.mp4)」を押すと「登録しました」が出て、お題が次の本数に進む。`ls /tmp/rec_try/raw_jsl/*/` と `cat /tmp/rec_try/raw_jsl/index.tsv` で確認
   - 破棄・撮り直しのあと `ls $TMPDIR/attention-capture-*`(`echo $TMPDIR` の場所)に `take-*.mp4` が残っていないこと。アプリを閉じたあと `pgrep -fl "ffmpeg|pose-extract"` に何も出ないこと
   - 録画中にアクティビティモニタで CPU と温度(発熱)、10 秒録画して「コマ落ち」の注意が出ないこと
6. 撮った動画の確認: `ffprobe -v error -select_streams v:0 -show_entries stream=codec_name,width,height,r_frame_rate,pix_fmt,bit_rate,nb_frames -of default=nw=1 /tmp/rec_try/raw_jsl/*/01.mp4`(h264 / 1620 / 1080 / 30/1 / yuv420p / 約 7〜8Mbps)
7. 問題なければ `ATTENTION_DATA_DIR` を外して(既定の `transformer_burn/data/raw_jsl`)本番の撮影に使う。**この場合、画面に「本物のデータに書き込みます」と出る**ことを確認してから使う
