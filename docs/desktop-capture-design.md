# デスクトップアプリでの撮影機能 設計案(提案・未決)

作成: 2026-10-12。**設計案であって決定ではない**。着手するか・いつやるかも未決。元になったのはユーザーのメモ(2026-10-12):
「学習データ作成の動画撮影を、デスクトップアプリでできるようにしたい。カメラプレビューに人の枠みたいなものを付けて『大体この辺にいてください』と示す。手指の認識ができているかをリアルタイムで見られると嬉しい」。

位置づけ: `docs/desktop-app-design.md` の **T2(撮影モード)**。同文書 §7 で「T2 は今回の範囲外」とされていたので、これはその範囲を広げる提案にあたる。**範囲を広げるかどうかはユーザー判断**。

## 1. 目的と、解きたい問題

今の撮影は OBS/QuickTime で録画し、`pose-extract` の撮影セッションが保存先を監視して取り込む方式。困りごと(CLAUDE.md の記録と実撮影の経緯から):

- 手が検出できたか(`ng_hands`)は**撮った後にしか**分からない。一人撮影で、撮り直しのコストが高い
- 立ち位置・画角が撮影日ごとにずれる(stage1 と stage2 で手の外側への伸びの最適オフセットが符号まで反転した、という実測がある)。CenterSquare の ROI は余裕がほぼ無く(手の 3.7% が切れる)、画角のずれが直接効く
- 一人撮影のため録画の前後に手を下げた時間が長い(検出区間は動画の半分弱)。開始・終了の操作ラグが質を落とす
- 次に何の語を何本目で撮るかを、別画面の進捗表示で確認している

## 2. 既にあって、そのまま使えるもの(コードで確認済み)

| 部品 | 場所 | 使い道 |
|---|---|---|
| カメラ入力(ffmpeg avfoundation、1920x1080 を 1620 幅に中央クロップ) | `pose_extractor/src/live.rs` の `CameraSource` | 既存の撮影データ(1620x1080、30fps、h264 約 7.7Mbps)と同じ画角で撮れる |
| 手の骨格・検出範囲(CenterSquare 枠)のリアルタイム重ね描き | `desktop/src/overlay.rs`、エンジンの `preview` イベント | 「手指の認識ができているか」の要望の大部分は、**既にライブ認識画面にある** |
| 鏡像表示(表示のみ反転、保存は反転しない) | `desktop/` | そのまま |
| 語リスト・撮影数の集計・次の語の選択 | `progress.rs`(`load_words` / `merge_index` / `next_word`) | お題の表示に使える |
| 取り込み(命名 `<word_id>_<romaji>/<rep>.mp4`、`index.tsv` 記帳) | `progress.rs` の `ingest` | 保存後の記帳をそのまま使える |
| 手検出の合否判定(連続して検出できた最長区間 1.0 秒以上) | `progress.rs` の `HandChecker` / `MIN_HAND_RUN_SECONDS` | 撮影直後の合否表示に使える |
| 人物の肩位置(153 テイク分) | 今回作った `body_sequence`(`pose_dict_full_center_body.json`、gitignore 対象) | 立ち位置ガイドの基準位置を、実データの中央値から決められる |

つまり**新規に作る必要があるのは、(a)アプリ内録画、(b)立ち位置ガイドの描画、(c)お題・合否の画面、の 3 つ**。

## 3. 守るべき境界(ユーザー明示の制約、desktop-app-design.md §1 から)

- ライブ認識の経路は映像・特徴量を保存しない
- 撮影モードは**別モード**。書き込みはそのモードの間だけ、画面に録画中であることを常に明示する
- **モード間で書き込み経路のコードを共有しない**

設計への含意: 録画・保存は `capture` という別モジュール(エンジン側 `pose_extractor/src/live/capture.rs` を新設)に閉じる。ライブ認識のコードから `capture` を呼ばない。テストで「ライブ認識モードでは `raw_jsl` にも一時領域にもファイルが 1 つも増えない」を固定する(§7)。

## 4. 構成の提案

### 4.1 カメラは 1 本だけ開き、エンジンが録画も担う(推奨)

案:
- **案1(推奨): エンジンが 1 本の ffmpeg で受けた生フレームを、(a)認識/プレビュー用と、(b)録画用エンコーダ(別の ffmpeg、stdin に生フレーム)の両方に流す。** カメラを二重に開かない。録画の画質を既存データ(1620x1080・30fps・h264)に揃えられる
- 案2: アプリ(GUI)側が別に ffmpeg でカメラを開いて録画する。**macOS のカメラを 2 プロセスが同時に開けるか、フレームレート・形式が競合しないかは未検証**で、プレビュー(エンジン)と録画(GUI)で映像がずれる懸念もある。不採用を推奨

案1 の注意点(未検証):
- 録画用エンコーダが重くなると認識・プレビューが遅れる。撮影モードでは**認識(語の推論)は止めて、手検出(骨格表示と合否)だけ動かす**のが現実的。負荷は撮影モード専用に測る
- 生フレームを 2 箇所へ流す分の CPU/メモリ。1620x1080x3 バイト x 30fps は約 150MB/秒で、パイプ 1 本ぶんは既に支払っている。エンコーダへの追加ぶんの実測が要る
- 録画の画質設定: 既存データは約 7.7Mbps の h264。同じ設定に揃えるか、より高画質(crf を下げる)にするか。**エンコード設定が違うと手検出に微妙に効く可能性がある**が、測っていない(未確定)

### 4.2 エンジンとの会話(追加分の提案)

`--engine-json` の既存プロトコルに足す。ライブの `start` とは**別のモード指定**にする。

- 画面 → エンジン: `start` に `mode: "capture"`(お題の語 ID・テイク番号を渡す)/ `capture_record`(録画開始)/ `capture_stop` / `capture_accept`(採用)/ `capture_discard`(破棄)
- エンジン → 画面: `capture_state`(待機・カウントダウン・録画中・判定中)/ `capture_saved`(保存先、長さ、手検出の最長連続区間の秒数、合否の見立て)
- 録画中は一時領域(例: リポジトリ外の作業用ディレクトリ)に書き、**採用したときだけ** `raw_jsl/<word_id>_<romaji>/<rep>.mp4` へ移して `index.tsv` に記帳する。破棄なら一時ファイルを消すだけ。`raw_jsl` を汚さない

### 4.3 立ち位置ガイド

- 表示: プレビュー(鏡像)の上に、頭と肩の輪郭の半透明の枠を重ねる。枠の位置と大きさは、既存 153 テイクの肩中心・肩幅の**中央値**から決める(`body_sequence` から計算。動かない定数でよい)
- 目的は「だいたいこの辺」。**厳密さは不要**(実験の結果、肩基準にしても認識精度は変わらなかったので、位置の揃えは精度のためではなく、**手が CenterSquare 範囲に収まる確率を保つため**)
- 提案: 最初は静的な枠のみ。**リアルタイムで人物を検出して「ずれています」と出す機能は後回し**(人物検出+BlazePose を毎フレーム/数 fps で回す分の負荷が要る。必要になったら追加)
- 手が検出範囲(CenterSquare の枠)からはみ出しそうなときの警告は、骨格が既に出ているので、**手の点が枠の縁に近づいたら枠を赤くする**程度で足りる見込み(方向・指示語で手が切れやすいという実測に直接効く)

### 4.4 リアルタイムの手指認識表示

既に実装済みの骨格・枠の重ね描きをそのまま使う。撮影モード用の追加は次の 3 つ:

- 左右どちらの手が今検出されているか(`status.hands` の L/R/LR)を大きく表示
- 「連続して手が検出できている秒数」を実行中に表示し、合格ライン(1.0 秒)を超えたら色を変える(撮影後の判定と同じ基準を、撮影中に見せる)
- 録画中に手が一度も検出されていないときの警告

### 4.5 お題の表示と記帳

- 画面に「次の語: こんにちは(001)、3 本目 / 目標 10」を大きく出す。語リストと進捗は `words.tsv` と `index.tsv` から読む(`progress.rs` の関数を呼ぶ)
- 取り込みは `ingest` をそのまま使う(命名・`index.tsv` 記帳・合否の記録)。撮影モード専用の書き込み経路にしたいので、`ingest` 本体を共有する場合は**撮影モード側からの呼び出しだけ**にし、ライブ認識側からは到達できないことをテストで確認する
- 使用手(左手を約 10% 含める方針)の案内を出すかは**未決**(現状は撮影者の判断。画面が「今回は左手で」と指示する機能は、方針の運用を変えるのでユーザー判断)

### 4.6 録画の開始・終了

一人撮影のラグ対策として、次を提案する(どれも未決):

- **カウントダウン開始**: 開始キーを押して 3 秒後に録画開始(席に戻る時間)
- **自動終了**: 手が下がり、検出が一定時間(例 2 秒)途切れたら自動で録画を止める。これで後ろの手ぶら時間が減る
- 手動の開始/終了も残す
- 長さの目安(`DURATION_MIN_MS`=2 秒、`DURATION_MAX_MS`=10 秒)を超えたら警告

## 5. 段階の提案

各段階だけで使えるようにして、途中で止めてもよい形にする。

| 段階 | 内容 | 書き込み | 規模の見込み |
|---|---|---|---|
| R0 | 撮影用の画面: 立ち位置ガイド枠、手の連続検出秒数と L/R の表示、お題と進捗の表示(読み取りのみ)。**録画はしない**。今までどおり OBS/QuickTime で撮る | なし(`index.tsv` も読むだけ) | 小。ライブ認識画面の流用が中心 |
| R1 | アプリ内録画: エンジン側 `capture` モジュール、一時領域への録画、採用で `raw_jsl` へ取り込み。撮影直後の合否表示 | 採用時のみ | 中。ffmpeg の 2 本目、負荷測定、境界のテストが要る |
| R2 | カウントダウン・自動終了・撮り直しの操作性 | 同上 | 小〜中 |

**R0 から始めるのを推奨**(撮影中の今日からでも、OBS と併用できる)。R0 は何も保存しないので、データの境界に触れない。

## 6. 技術的な論点とリスク

| 論点 | 見立て | 確度 |
|---|---|---|
| 認識を止めて手検出だけにする場合の負荷 | 手検出のみなら現行ライブ(約 15fps)より軽い見込みだが、エンコーダ追加ぶんを含めた実測は無い | 未検証 |
| カメラの fps | 既存データは 30fps。ライブ認識は約 15fps(CAMERA_FPS)。**撮影モードで 30fps を取れるか**が未確認 | 未検証。最初に確かめる |
| 画角の一致 | ライブ用の入力は 1920x1080 を 1620 幅に中央クロップ(既存データと同じ 1620x1080)。ただし**既存データが実際にどのカメラ・設定で撮られたかは記録が無い**(OBS/QuickTime、外付けか内蔵か) | 同じカメラかどうかの確認をユーザーに聞きたい |
| 画質差による認識への影響 | アプリ内録画と OBS 録画で、エンコード設定が違う動画が混ざる。手検出・手形記述子への影響は測っていない | 未検証。混ぜる前に、同じ語で両方撮って dict を作り比較するのが安全 |
| `ingest` の再利用 | `progress.rs` の `ingest` は非公開関数。`pub(crate)` にするか、取り込み専用の関数を切り出す必要がある | コードで確認 |
| 録画中の操作 | 一人撮影ではキーボード操作が難しい場合がある。フットスイッチ等は不要としても、**手の動き(例: 両手を一度大きく上げる)で開始する**案もある | 未検討 |
| 同意書との関係 | 協力者が撮影に使う場合、アプリ内で同意の確認が要る可能性がある(`nft` リポジトリ側の議論)。**現在のデータはすべて開発者本人** | 協力者が現れたときの別論点。今回は扱わない |

## 7. 検証方法

- エンジン: 偽の ffmpeg を使った統合テストの流儀(既存)。`capture_*` イベントの形を固定する golden テスト
- **境界のテスト**: ライブ認識モードで start→quit を流しても、`raw_jsl` と一時領域にファイルが増えない。撮影モードで破棄したとき、一時ファイルが残らない
- 実機: カメラ 30fps で録画した動画が既存データと同じ解像度・fps になること。録画中の発熱と、認識停止時の CPU。終了後に ffmpeg が残らないこと(既存の確認項目)
- 取り込みの往復: アプリで撮った 1 本を `build-dict` に通して手ポーズ列が出ること

## 8. 未決(ユーザーの判断待ち。矢印は私の推奨で、決定ではない)

1. **範囲を広げるか**: desktop-app-design.md §7 の「T2 は範囲外」を変更してよいか → R0 だけ先に、R1 以降は撮影の手間の実感を見てから
2. **既存データのカメラ**: 既存の `raw_jsl` は何で撮ったか(内蔵 FaceTime か外付けか、OBS か QuickTime か)。画角を揃える基準になる → 教えてもらえれば R0 のガイド位置の検証に使う
3. **撮影モードで認識を止めるか**: 負荷と、データの境界(撮影中にライブ認識を動かさない)の両面から → 止める
4. **録画の画質**: 既存に揃える(約 7.7Mbps)か、高画質にするか → 既存に揃え、混在の影響は先に測る
5. **使用手の案内**: 画面が「今回は左手で」と示すか → 示さない(現行の運用を変えない)
6. **自動終了・カウントダウン**: 入れるか、秒数 → R2 で、実際に使いながら決める
7. **立ち位置ガイド**: 静的な枠のみか、リアルタイム検出でずれを知らせるか → 静的のみ
8. **ブランチ**: ルールは `feature/`。新規は `feature/desktop-capture` を `feat/desktop-app` の履歴から切る案(`feat/desktop-app` は PR #16 でマージ済み)

## 9. R0 実装記録(2026-10-12、ブランチ `feature/desktop-capture`。事実の記録で、新しい決定ではない)

R0(撮影ガイド。録画なし・書き込みなし)を `desktop/` に実装した。§8 の未決のうち 1(範囲)はユーザーの指示で R0 だけ着手、7(立ち位置ガイド)は静的な枠のみで実装した。他の未決はそのまま。

### 9.1 実装した内容

- **モード切替**: ライブ認識画面の操作欄に「モード: ライブ認識 / 撮影ガイド」のボタンを追加(停止中のみ切り替え可)。撮影ガイドでは右列が「次の語・手の検出・検出範囲・凡例」に変わる。ライブ認識の右列・操作・挙動は従来どおり
- **エンジンの使い方**: 撮影ガイドでは `start` を区切り方「手動」で送り、開始操作(`toggle`)は送らない(ボタンを出さず、スペースキーも無視)。`result` イベントが来ても表示しない(動画入力 + 手動ではエンジンが再生開始と同時に記録して終端で認識するため、来ることがある)。ライブ認識で選んでいた区切り方は、撮影ガイドの `ready`/`segmenter` で上書きしない。**pose_extractor のコードとエンジンの JSON 仕様は変更していない**
- **立ち位置ガイド**(`desktop/src/capture_guide/silhouette.rs`): 鏡像プレビューに、頭(楕円)と首・肩・腕の輪郭を白の半透明(不透明度 0.6)で描く。位置と大きさは下の定数(データの中央値)から決め、頭の大きさ・首肩の形の係数は目視で調整した目安(データ由来ではない)
- **手の検出**(`hand_run.rs`): `status.hands` を大きく「左手 / 右手 / 両手 / 手なし」で表示。左右別々に「連続して検出できている秒数」を数え、良い方を表示。1.0 秒以上で緑(未満は琥珀色)、色だけに頼らないよう「合格ライン以上 / 1.0 秒未満」の文字も出す。途切れたら「直前の連続区間: X 秒」も出す
- **縁の警告**(`edge.rs`): 手の点が検出範囲(`preview.crop`)の縁から枠の幅・高さの 3%(`EDGE_MARGIN_RATIO`)以内、または枠の外にあれば、枠を赤く太く(黄・2px → 赤・5px)し、「検出範囲の右の縁に手が近づいています。枠の内側へ」のように、画面に見えている向き(鏡像)で知らせる
- **お題と進捗**(`progress.rs`): 「次の語」を大きく(例: `かれ(011)` と `4 本目 / 目標 10`)、全体の本数・完了語数を小さく表示。3 秒ごとに読み直す(撮影中に他のツールが動画や index.tsv を足すため)。読めないときは赤い枠に日本語の理由を出し、他の機能は動かす
- **データの場所**: 環境変数 `ATTENTION_DATA_DIR`、無ければ `<リポジトリ>/transformer_burn/data/raw_jsl`(リポジトリの場所は既存の `ATTENTION_ROOT` の解決と同じ)
- **開発・検証用の環境変数**: `ATTENTION_APP_MODE=capture-guide` で撮影ガイドから起動。`ATTENTION_APP_DEBUG` 有効時、撮影ガイドの表示内容(手・秒数・合格判定・直前・縁・お題)を変化時に標準エラーへ 1 行出す

### 9.2 規則の出典と、progress.rs との違い

- 合格ライン 1.0 秒・瞬断 1 サンプルの橋渡し・左右の良い方で判定 = `pose_extractor/src/progress.rs` の `MIN_HAND_RUN_SECONDS` / `MAX_RUN_GAP_SAMPLES` / `ingest`。ただし近似で、厳密には一致しない:
  - 秒数の数え方: progress.rs は「検出サンプル数 / サンプル毎秒」、ここは「区間の最初の検出時刻〜最後の検出時刻」(差はおおむね 1 サンプル間隔)
  - 1 サンプルの長さ: エンジンの status は最大 10 回/秒なので瞬断の許容は約 0.1 秒。progress.rs(約 3 サンプル/秒)では約 0.33 秒
- **経過時間は「読み取りスレッドが status 行を受け取った時刻」**。status/preview の JSON に時刻が無く、`rec_secs` は記録しない撮影ガイドでは 0 のまま使えないため。UI が Inbox を見る時刻にしなかったのは、Inbox の status が最新 1 件だけを残す作りで途中のサンプルが消えるため(サンプルは別キューに全件積む)。カメラでは受信時刻がカメラの時刻とほぼ一定の遅れで進む見込み(実カメラでは未確認)。動画入力ではエンジンが最速で処理するので動画の時刻とは一致しない
- 次の語 = progress.rs の `load_words` / `scan_takes` + `merge_index` / `take_counts` / `next_word` と同じ規則を `desktop` 側に再実装(pose_extractor への依存は足していない)。ファイルが正で、index.tsv は quality_flag を引くためだけに使う。`ng` で始まる quality_flag は数えない。セッションの「スキップ」は無い。**progress.rs と違い、words.tsv が無くてもテンプレートを書き出さない**(読めない理由を表示する)

### 9.3 立ち位置ガイドの定数(元データ)

### 9.7 ユーザー判断が要る点(推奨は添えるが、決定ではない)
