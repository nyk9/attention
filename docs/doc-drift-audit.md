## 分類の基準

| 分類 | 定義 | 扱い |
|---|---|---|
| **事実誤り** | 実体を見れば一意に決まる(寸法・件数・依存関係・ファイル名) | そのまま直してよい |
| **決定領域** | どちらに寄せるかがユーザーの判断(語彙数・テイク数・ロードマップの目標値) | **食い違いの指摘まで。数値を決めない** |
| **曖昧** | 記述は誤りではないが、読み手が別の意味に取りうる | 補足を足す |
| **陳腐化** | 当時は正しかった状態記述が更新されていない | 現況に合わせるか、日付を明記して履歴化 |

## B'. もう一つの失敗の型: 書いてあるのに参照されない

B10 は他の項目と性質が違う。ドキュメントが**間違っていた**のではなく、**正しかったのに読まれなかった**。

同種の例:
- CLAUDE.md は 2026-07-02 の時点で「build-dict は各テイクから均等10フレームを抜くため、
  手ぶら時間が長いテイクは学習特徴としても質が落ちる」と書いていた。
  2026-08-22 に位置別検出率の∩字を実測して初めて手が付いた(約7週間)
- CLAUDE.md の「モデル設定 d_model=16」は古かったが、**正しい値は config.rs にあった**

**含意**: C1〜C3(出典併記・種別マーク・自動チェック)は「記述を実体に合わせる」対策であり、
この型には効かない。**長大な単一ファイルの中で、関連する記述が離れた場所にあると参照されない**
という別の問題なので、C4(現況と決定ログの分離)や、節ごとの「既知の落とし穴」欄のような
構造的対策が要る。

## C. 再発防止の提案

観測された失敗はすべて同じ型:**ドキュメントの数値を、実体を確認せずに引用した**。
このセッション群で確認されただけで6回以上発生している。個人の注意力ではなく構造で防ぐ。

### C1. 数値に出典を併記する記法を決める(最優先・コスト最小)

数値の直後に、どうやって確認できるかを書く。

```
- 語彙: 74語 [実測 2026-08-22: awk 'NR>1 && NF' data/raw_jsl/words.tsv | wc -l]
- d_model: 64 [出典: transformer_burn/src/config.rs:2]
- 撮影目標: 740テイク [算出: 74語 × target_takes=10]
```

**派生値(計算結果)は結果だけを書かず、必ず入力と式を書く。**
「547テイク」が古くなったのは、語数が変わったのに結果だけが書かれていたため。

### C2. 数値の種別をマークで区別する

同じ表に **実測値・目標値・仮定値・決定値**が混在しているのが誤読の温床
(「top-5 78-82%」の取り違えも、判断根拠の数値を成績と読んだもの)。

`[実測]` `[目標]` `[仮]` `[決定 YYYY-MM-DD]` の4種を数値に付ける。
特にロードマップ表の「語彙数(仮)」「動画総数(仮)」は既に(仮)と書かれているが、
**行ごとに実測・目標・仮が混ざっている**ので、セル単位で付けるほうがよい。

### C3. 機械チェック可能な項目をテスト化する(効果が最も大きい)

CLAUDE.md にマーカーを埋め、実体と突き合わせるテストを置く。

```markdown
- **語彙**: <!-- fact:words_count --> 74 語
```

```rust
// transformer_burn/tests/doc_facts_test.rs
#[test]
fn claude_md_facts_match_reality() {
    // CLAUDE.md の fact マーカーを読み、words.tsv / config.rs の実体と比較
    // 不一致なら「どちらが正しいか人間が判断せよ」というメッセージで落とす
}
```

チェック対象の候補(いずれも一意に決まる):
words.tsv の語数 / stage 別語数 / index.tsv の ok テイク数 / config.rs の各 const /
Cargo.toml の依存クレート / 撮影データの解像度 / pose dict のタグ数

**注意**: テストは「不一致」を検出するだけにし、**どちらに寄せるかは自動で決めない**。
決定領域の数値を機械が上書きすると、今回より悪い事故になる。

### C4. 「現況」と「決定ログ」を分離する

CLAUDE.md が、**時点の状態**と**決定の履歴**と**将来の計画**を同じ節に混ぜている。
B6 の事故(訂正が別の政策判断と抱き合わせで Revert された)は、この混在が直接の原因。

- 決定ログ: 追記のみ。日付と決定者を明記し、**後から書き換えない**
- 現況: 実体から生成できるものは生成する(C3 のマーカーと同じ情報源)
- 計画: 前提が変わったら引き直す。前提そのものを明記する

### C5. 実験記録の書き方を統一する

`docs/experiments/` の記録で、**結論の表を文書の先頭に置く**。考察文の中に出てくる数値は
判断根拠であって成績ではないので、**考察では数値を再掲しない**か、再掲するなら
「(この値はレンジの重なり幅であって成績ではない)」のように明示する。

### C6. Revert の運用

複数の変更を1コミットに混ぜない。B6 は「数値の訂正」と「政策判断」が同じコミットに
入っていたため、政策判断を戻したら数値の訂正も巻き添えになった。
