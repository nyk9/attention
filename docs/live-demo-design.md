# ライブ手話認識デモ 設計と実装記録

作成: 2026-10-11。**L0(fps 実測)と L1(Enter で録画開始/停止)は実装済みで、実機のカメラで動作確認が取れた**(記録は §8)。**L2(自動区切り)は実装済みで、実機のカメラで「ちゃんとできていた」とユーザーから報告があった(§8.7。閾値の当たり具合を測った記録は無い)。L3(表示の仕上げ)は未着手**。

## 目的とスコープ

- 目的: 友人に「今やっていること」を見せる。Mac 内蔵カメラの前で手話をすると、画面に単語(タグ)が出る
- 理想: 起動中は常時監視して自動認識。最低ライン: キー操作で録画開始/停止 → 結果表示
- やらないこと: 精度目標(70%)の達成、日本語文への整形、友人の手話の認識、語彙追加
- 運用: 別ブランチで作り、必要になったら本流へマージ

## 1. 全体構成

```
ffmpeg(avfoundation, 1920x1080 → crop 1620x1080, rgb24)
   │ stdout パイプ
   ▼
[読み取りスレッド] read_exact で1フレームずつ読み、「最新フレーム置き場」を上書きするだけ
   │ (推論が追いつかない分は捨てる = 遅延が溜まらない)
   ▼
[メインループ] 最新フレームを取り出す
   → infer_frame_feature(既存, :1334)= Palm + Hand → (126次元, 左手有無, 右手有無)
   → (時刻, 126次元, 左, 右) をバッファへ
   → 区切り判定(L1: キー / L2: 手の有無の状態機械)
   → 区切れたら: バッファから10フレーム選択(既存の純粋関数)
   → Predictor(モデルを起動時に1回だけ読み込む)→ 上位k
   → 端末に表示
```

- 新規ファイル `pose_extractor/src/live.rs` に閉じ込める。`main.rs` の変更は `mod live;` とメニュー1項目のみ
- **フレームの入力元を差し替え可能にする**(カメラ / 動画ファイル)。動画ファイルを入力にすれば、カメラなしで区切り・選択・推論の全経路をテストできる(§4)

## 2. 段階

| 段階 | 内容 | 終了条件 |
|---|---|---|
| L0 計測 | フレームあたりの Palm/Hand 所要時間とカメラの実効 fps を測る | 数値が出る。L1 の窓の設計値(処理 fps)が決まる |
| L1 半自動(最低ライン) | Enter で録画開始 → もう一度 Enter で停止 → 結果表示 | 友人の前で動く |
| L2 自動 | 手の出入りで自動的に区切る。L1 の操作も残す | 起動しっぱなしで単語ごとに結果が出る |
| L3 仕上げ(任意) | 語彙一覧・日本語ラベル表示・直近の結果の履歴 | 見せ方が整う |

**L1 と L2 は「区切り方」だけが違い、区切った後(選択 → 推論 → 表示)は共通**。L1 を作れば L2 は状態機械1つの追加で済む。L2 に届かなくても L1 が逃げ道として残る。

## 3. 論点ごとの提案

### 3.1 fps の実測方法(L0)

既存の測定用テスト(`measure_palm_roi` などの `#[ignore]` テスト)と同じ形で、測定専用のテストを1本足す。

1. **推論側**: raw_jsl の既存動画(例: 数本)を全フレーム処理し、フレームごとに `run_palm_detection_mode` と `run_hand_landmark`(手の数だけ呼ばれる)の所要時間を `Instant` で測る。**検出された手の数(0/1/2)別に**中央値・90%点を出す。手が2本のフレームは Hand 推論が2回なので一番遅い
2. **カメラ側**: avfoundation から10秒読み、実際に届いたフレーム数と、1フレームの読み取り間隔を測る
3. 判断材料(実測結果は §8.2。処理 fps は中央値で約12〜18、実機カメラで約13〜17 で、下記の約7を上回った): 1サインの長さ(手が写っている区間)を約1.5秒と置くと、窓あたり10フレームを確保するには**処理 fps ≥ 約7** が要る。下回る場合は `downsample_indices` が同じフレームを重複して選ぶ(動作はするが学習時と分布がずれる)。その場合の対策は、Palm を数フレームおきにして直前の手の位置から Hand だけ回す(MediaPipe 本来の追跡方式)だが、**測ってから判断**

### 3.2 窓の切り出しと学習分布のずれ(最大のリスク)

学習データの選択フレーム10枚のうち、手が写っている枚数は dict の作り方で大きく違う(`docs/experiments/sign-span-frame-selection.md`):

| dict | 位置0〜9の手の検出率 | 手あり平均 | 精度(20 runs) |
|---|---|---|---|
| center + 均等間隔 | 1 / 30 / 95 / 97 / 90 / 49 / 7 / 0 / 0 / 0 % | 3.69/10 | top-1 68.8% / top-5 88.5% |
| center + サイン区間 | 47 / 95 / 94 / 96 / 98 / 99 / 100 / 99 / 97 / 41 % | 8.68/10 | top-1 69.0% / top-5 87.8% |

均等間隔で学習したモデルは「前に少し空白、サインは前半、後ろ4割は空白」という一人撮影特有の形を前提にしている。ライブでこの形を再現するのは難しい(人がキーを押すタイミング次第で毎回変わる)。

**提案: サイン区間 dict で学習したモデルを使い、ライブ側も同じ規則で区間を切る。**

- 精度は均等間隔と差がない(上表、p=0.89)ので失うものが無い
- ライブでは区間検出のコストがゼロ(§0 #3)
- L1(キー操作)でも L2(自動)でも、**区切った後は「バッファ内の手あり最長区間 → 前後に余白 → 10枚等間隔」という同じ処理**になる。キーを押すタイミングの揺れを吸収できる
- 学習時の規則との対応: 学習時は「16点サンプルの最長区間(瞬断1つまで橋渡し) + 前後に step/2 の余白」。ライブは処理フレームが(設計時の想定で約8fps、実測では約12〜18fps。§8.2)と学習時の一次パス(4秒動画で約4fps)より細かいので、**余白は秒で揃える**(4秒・120フレームの動画で step=7、step/2=3フレーム ≈ 0.1秒)。瞬断の橋渡しも秒で揃える(1サンプル=7フレーム ≈ 0.23秒)
- 既知の小さな差: 学習時の区間判定は Palm のみ、ライブは Palm+Hand まで通った結果。コードのコメントにある通り後者はわずかに厳しい(1530フレーム中 28 フレームの差)。デモ用途では無視できる範囲と見るが、気になれば Palm の結果だけで判定することもできる

### 3.3 L2 自動区切りの状態機械

```
待機 ──(手あり が 0.3秒続く)──▶ 記録中 ──(手なし が 0.5秒続く)──▶ 確定 → 推論 → 待機
                                    └──(記録が 6秒を超える)──▶ 確定(打ち切り)
```

- 記録開始時に直前の約0.5秒も含める(リングバッファ)。区間の余白に使う
- 確定時に区間が短すぎる(例: 0.4秒未満)なら捨てる(手がカメラをかすめただけ)
- 状態機械は「(時刻, 手あり)を1つずつ受け取り、確定した区間を返す」純粋な構造体にして、ユニットテストで閾値の境界を固定する
- 数値はすべて仮置き。L0 の実測と、実際に試した感触で調整する

### 3.4 サインしていないときに誤った結果を出さない

このモデルには「何もしていない」クラスが無く、何を入れても51語のどれかが出る。対策は3段:

1. **区切りで止める(主対策)**: 手が写っていなければ記録が始まらないので、推論そのものが走らない
2. **長さで止める**: 短すぎる区間は捨てる(§3.3)
3. **確信度の表示(補助)**: top-1 の確率が閾値(仮 0.5)未満なら「自信なし」と添えて上位3件を並べる。ただし CLAUDE.md の pipe-v2 測定で記録されている通り、このモデルは **0.7〜1.0 の高確信度で外すことがある**ので、確率は誤りを止める仕組みとしては弱い。見せ方の工夫と位置づける

注意点: MacBook の前に座ると、キーボード上の手がフレーム下端に写る可能性がある。学習データでは「手を下げた状態 = フレーム外」なので、写ると記録が始まってしまう。**L0 のカメラ確認で実際に写るかを見る**。写る場合は「手首の y がフレーム下端付近なら手なし扱い」の条件を足す。

「何もしていない」クラスを学習させる方法(無サインの動画を集めて学習)もあるが、データ作りが要るのでスコープ外とする。

### 3.6 カメラ入力

- **アスペクト比**: FaceTime HD カメラ(1080p)を 1920×1080 で取り、ffmpeg の `crop=1620:1080` で中央を切ると、学習データと**同じ 1620×1080** になる。座標は幅・高さで正規化され、手首の画像内座標は効く特徴(実験3)なので、解像度・縦横比は揃える。CenterSquare ROI(中央 1080×1080)も学習時と同じ位置になる。1920×1080 での取り込みは実機で動作した(`-video_size 1920x1080` を指定して認識結果が出た。§8)
- **ffmpeg の引数(実装済みの `camera_ffmpeg_args`)**: `-nostdin -hide_banner -loglevel error -f avfoundation -framerate 30 -video_size 1920x1080 -i 0:none -vf crop=1620:1080 -fps_mode passthrough -pix_fmt rgb24 -f rawvideo -`。**`-nostdin`(+ 子プロセスの stdin を null)と `-fps_mode passthrough` は実機確認で必要と分かって加えたもの**(理由は §8.4)
- **撮影条件の差**: raw_jsl をどのカメラ・どの距離で撮ったかで、ずれの大きさが変わる。**ユーザー回答(2026-10-11): このMacの内蔵カメラで撮影**。カメラ由来の差は無く、座り位置・照明の差だけが残る
- **左右反転**: avfoundation は反転していない映像を返す(QuickTime のプレビューは鏡像だが、録画ファイルは反転なし)。学習データと同じ向きかを1回確かめる(右手でサインして右手枠に入るか)。**確認の記録は無い(未確認)**
- **遅延**: 1フレーム 1620×1080×3 = 約5.2MB。30fps で約157MB/s がパイプを流れる。推論が追いつかない分は読み取りスレッドで捨てる(最新のみ保持)。帯域が気になれば ffmpeg 側で `fps=15` を足す(実機では処理が約13〜17fps に収まり、足していない。なお映像停止の対策としては `fps=30` フィルタも効いた。§8.4)
- **権限**: 初回はターミナルアプリ(Ghostty / iTerm / Terminal.app など)にカメラ権限のダイアログが出る。拒否された場合はシステム設定 → プライバシー → カメラで許可する
- **ONNX セッション**: 起動時に1回だけ読み込む(`recognize_wizard` は呼ぶたびに読み込んでいる)

### 3.7 表示

端末のみ(GUI は Phase 0b で凍結中なので作らない)。

```
語彙(51語): こんにちは / おはよう / ... (起動時に一覧表示。words.tsv の label_ja を使う)

[待機中] 手: --                         ← \r で1行を書き換え
[記録中 1.2s] 手: R
→ ありがとう (arigatou) 0.83   候補: おねがいします 0.10 / すみません 0.04
```

- 語彙一覧の表示は、語彙外の語を出すと必ず別の語になることを見ている人に伝えるため(引き継ぎの提案どおり採用を推奨)
- タグ → 日本語ラベルの置き換えは `words.tsv` の `label_ja` 列を引くだけ(51タグ全部が `romaji` 列と一致することを確認済み)。これは表示の置き換えであって、スコープ外の「日本語文への整形」ではない
- 直近5件程度の結果を履歴として残す(L3)

## 4. 検証方法

カメラが無くても回せるものを優先する。

| テスト | 種類 | 内容 |
|---|---|---|
| 区切りの状態機械 | ユニット | 手あり/なし列を与え、開始・確定・打ち切り・短区間破棄の境界を固定 |
| ライブ用フレーム選択 | ユニット | バッファから最長区間 + 余白 + 10枚、の結果が既存 `span_indices` の規則と一致 |
| **動画ファイルをライブ経路に流す** | スモーク(`#[ignore]`) | raw_jsl の1本を「カメラの代わり」に流し、選ばれる10フレームと推論結果が、同じモデルで既存の認識経路に同じ動画を渡した結果と大きく食い違わないこと(処理 fps が違うので完全一致はしない) |
| fps 計測 | 測定(`#[ignore]`) | §3.1 |
| カメラ | 手動 | 実機で数語やってみる。`TTY 必須` なので自動化しない |

## 5. ブランチ運用

ブランチ `feat/live-demo` を main から切る。**本流に先に入れてよいもの**と**デモ固有のもの**をコミットで分ける。

| 順 | コミット | 本流への取り込み |

### 8.2 L0 実測(事実)

条件: raw_jsl の動画16本・1761フレーム、release ビルド、CenterSquare、動画のデコード時間は含まない。Palm 検出が見つけた手の数別の、フレームあたり所要時間(Palm + Hand 合計)の中央値。

|---|---|---|
| 0本 | 56.1 ms | 17.8 |
| 1本 | 71.4 ms | 14.0 |
| 2本 | 84.1 ms | 11.9 |

実機カメラでの処理 fps は約13〜17 だった。窓あたり10フレームを確保するための目安(約7、§3.1)は上回っている。

### 8.3 動画ファイルスモーク(事実)

`live_file_smoke`(`#[ignore]`)。学習済みの5本を「カメラの代わり」にライブ経路へ流し、同じモデルで既存の認識経路に同じ動画を渡した結果と top-1 を比べた。

- stride=1(全フレーム処理): 5/5 一致
- stride=4(約7.5fps 相当): 4/5 一致。`011_kare/01` が dame 0.66 になった
- 推測: stride=4 での食い違いは、間引きの位相によって選ばれるフレームが変わることによると考えられる(位相を変えた比較はしていない)。処理 fps が下がると結果が変わりうる例として記録する

### 8.4 実機で見つかった問題と対処

1. **ffmpeg が端末の標準入力を奪い、Enter / q が効かなかった**(事実)。ffmpeg は既定で標準入力を読む。対処: `-nostdin` と、子プロセスの `stdin(Stdio::null())` を加えた(実装済み)
2. **映像が止まり、1枚目のフレームだけが延々と複製された**(事実)。avfoundation 入力をライブ引数のまま rawvideo パイプに出すと起きる。実測: 90枚中、異なる画像は1枚。`-fps_mode passthrough` で解消(60枚中60枚が異なる)。`fps=30` フィルタの追加でも解消した。`-use_wallclock_as_timestamps 1` は解消しなかった。対処: `-fps_mode passthrough` を採用(実装済み)。推測: 出力が一定フレームレート扱いになり、avfoundation の時刻とずれて複製されたと考えられる(コード中のコメントも同じ見立て。時刻の中身は確認していない)
3. **Ctrl+C で終了すると、カメラ用 ffmpeg が孤児として残った**(事実)。SIGTERM が効かず `kill -9` が要った。`q` + Enter で終了した場合は正常に後始末される。**Ctrl+C 対策は未実装・未決**
4. **環境要因**(事実): 逆光、手が近すぎる、などを実機で確認。静止画での切り分け実験では、学習データの手を4倍に拡大すると片手が落ち、5倍で全滅した(手が画面で大きすぎると Palm 検出が落ちる)。この切り分け用の使い捨てテストは削除済み。推測: ライブでは手をカメラに近づけすぎない方がよい(撮影時の距離との差が効くため。距離と検出率の関係は網羅的には測っていない)
5. **デバッグ書き出し `LIVE_DEBUG_DUMP_DIR`(オプトイン)を追加した**(実装済み)。推論に渡したフレームを30枚に1枚、最大20枚、PNG で書き出す。`raw_jsl` / `models` / `pose_dict*` を含むパスは拒否する。既定はオフで、§6 の制約(ライブの映像・特徴量を既定で保存しない)に沿う。上記2の映像停止の発見に役立った

### 8.7 L2(自動区切り)の実装(実機でユーザーが動作を確認)

実装は `pose_extractor/src/live.rs` の `AutoSegmenter`(`Segmenter` トレイトを実装する純粋な状態機械。時刻はフレームの `t` だけを使い、実時間は読まない)。ウィザードで区切り方(自動/手動)を選べる。カメラの既定は自動。動画ファイル入力でも選べる(自動を選ぶと先頭の Toggle は押さず、手の出入りで区切る)。

閾値の初期値(**すべて仮置き**。`live.rs` の `AUTO_*` 定数):

| 定数 | 値 | 意味 |
|---|---|---|
| `AUTO_START_HAND_SECS` | 0.3 秒 | 手あり がこれだけ連続したら記録開始 |
| `AUTO_STOP_NO_HAND_SECS` | 0.5 秒 | 手なし がこれだけ連続したら確定 |
| `AUTO_MAX_RECORD_SECS` | 6.0 秒 | 記録がこれを超えたら打ち切って確定 |
| `AUTO_MIN_SIGN_SECS` | 0.4 秒 | 手が出ていた時間(最初の手あり〜最後の手あり)がこれ未満なら捨てる |
| `AUTO_REARM_NO_HAND_SECS` | 0.5 秒 | 打ち切り・手動停止の後、手なしがこれだけ続くまで次を始めない |
| `PRE_ROLL_BEFORE_ONSET_SECS` | 0.5 秒 | 手が出始めた時点より前に録画へ含める秒数。開始判定の 0.3 秒を足した 0.8 秒をリングバッファ長 `PRE_ROLL_MAX_SECS` にしている |

採用した挙動(設計 §3.3 に書かれていない部分を含む):

- **再アーム**: 6 秒打ち切りの直後に手が写り続けていると即座に次の記録が始まって同じ動きを二重に認識するため、打ち切り後は手なしが 0.5 秒続くまで再開しない。手動停止の後も同様
- **手動 Enter の併用**: 手動で始めた記録は手なしでも 6 秒でも自動停止せず、Enter で止める(L1 と同じ操作感)。自動で始めた記録中に Enter を押すとその場で停止して認識する(短さによる破棄はしない)。どちらも停止後は再アームを要求する
- **短い区間の破棄**: 自動停止のときだけ判定する(Enter での停止は判定しない)。捨てたときは `(短すぎる動きを無視しました)` を 1 行出す(結果行 `→ ...` とは区別)
- **pre-roll の取り方を実測で変えた**: 当初は「開始判定のフレームから 0.5 秒遡る」にしたが、実動画 8 本のスモークで `026_kuru/02` がサイン冒頭の短い手検出(約 0.2 秒)を落とし、`kuru` が `iu` 0.96 に変わった。手が出始めた時点から 0.5 秒遡る形(開始判定の分を足した 0.8 秒)に変更すると、同じ動画が `kuru` 1.00 に戻った
- 手あり判定は `LiveFrame::has_hand` 1 か所に集約(§3.4 のキーボード上の手の対策を足すならここ)。キーボード上の手は未対策

動画スモーク(`live_file_auto_smoke`、`#[ignore]`。`raw_jsl` を自動区切りで流す。カメラは使わない)の結果: 16 本中 16 本で結果がちょうど 1 件、先頭結果の top-1 が既存の認識経路と一致したのは 15/16 本(別の 8 本の組でも 8/8 本で 1 件、7/8 本で一致)。食い違った `025_iku/01`(kore 0.95)と `032_suki/03`(kirai 0.83)は、L1 の「動画全体を 1 回の録画にする」経路でも同じ答え・同じ区間になるため、自動区切りに起因しない(ライブ側と既存経路の差)。実機(カメラ)では、ユーザーが実際に試して「ちゃんとできていました」と報告した(2026-10 上旬。どの語を何回試したか、閾値が最適かの記録は無い)。閾値の調整は未着手のまま。
