# 部品C プロンプト v1 検証記録

- 実施日: 2026-07-02
- 実行モデル: claude-fable-5(Claude Code セッション内で prompt_v1.md を適用)
- **注意(検証の限界)**: この記録は「プロンプトを書いた本人(同一セッションの LLM)が
  その場で適用した」スモークチェックであり、評価者と実行者が文脈を共有しているため
  自己都合バイアスの可能性がある。本判定は **API 経由の独立実行(まっさらな文脈)** で
  行うこと。テストケースも n=8 の手作りで、頑健性の根拠にはならない

## テストケースと結果

TC2 は stage 1 の実評価(top-1 30%)で実際に起きた誤りをそのまま使っている。
他は語彙表(words.tsv 準拠)から構成した合成ケース。

### TC1: 1語・高確信(正常系)

```
スロット1: konnichiwa(0.99), ohayou(0.004), konbanwa(0.003)
```

出力:

```
整形結果: こんにちは
採用タグ: konnichiwa
```

所見: 期待どおり。1語はそのまま出て、文章に膨らまない(ルール4が効いている)。

### TC2: 高確信の誤認識(stage 1 実例: 正解 anata → arigatou 0.97)

```
スロット1: arigatou(0.97), onegaishimasu(0.02), sumimasen(0.005)
```

出力:

```
整形結果: ありがとう
採用タグ: arigatou
```

所見: 「ありがとう」と出るしかなく、**正解 anata が候補に無い誤りは整形側では救えない**。
これは想定どおりで、左右手ゆれ由来の高確信度誤りは認識側(部品B)の課題という
責任分界の確認になった。

### TC3: 文脈による top-k 挽回(部品Cの存在価値を測る中心ケース)

top-1 の組み合わせが意味的に破綻するように構成:

```
スロット1: sayounara(0.50), watashi(0.35), anata(0.10)
スロット2: taberu(0.90), nomu(0.07)
```

出力:

```
整形結果: わたしは食べます
採用タグ: watashi?, taberu
```

所見: 「さようなら+食べる」の破綻を検知して 2位の watashi を採用し、ルール5どおり
「?」が付いた。**ただしこの挽回は top-1 の組が明確に破綻しているときしか働かない**。
今の語彙(挨拶・代名詞・基本動詞の50語)では日本語がたいていの組を許容してしまう
(例: 「ありがとう、行きます」は不自然でない)ため、発動機会は限定的とみられる。
語彙の拡大と文長の増加で価値が上がる見込みで、②(LoRA)へ進む判断は stage 2 以降の
実文データで行うのが妥当。

### TC4: 確率拮抗

```
スロット1: hai(0.51), iie(0.49)
```

出力:

```
整形結果: はい
採用タグ: hai?
```

所見: top-1 採用+「?」で不確実性が伝わる。期待どおり。

### TC5: 挨拶の連続(2スロット)

```
スロット1: otsukaresama(0.90)
スロット2: sayounara(0.85)
```

出力:

```
整形結果: お疲れさまでした。さようなら。
採用タグ: otsukaresama, sayounara
```

所見: 活用・句読点の補い(ルール2)は自然。意味の追加はない。

### TC6: 通常の2スロット文

```
スロット1: watashi(0.85), anata(0.10)
スロット2: nomu(0.60), taberu(0.35)
```

出力:

```
整形結果: わたしは飲みます
採用タグ: watashi, nomu
```

所見: 正しく整形されたが、**nomu(0.60) vs taberu(0.35) に「?」が付かなかった**。
「拮抗」の判断が主観的なのは v1 の弱点(TC4 の 0.51/0.49 には付き、ここには付かない
境界が明文化されていない)。v2 では「top-1 と top-2 の差が 0.15 未満なら ?」のような
数値基準の明文化を検討する。

### TC7: 過剰生成の抑止

```
スロット1: sumimasen(0.95)
```

出力:

```
整形結果: すみません
採用タグ: sumimasen
```

所見: 期待どおり(「すみませんが、〜」のような続きを生成しない)。

### TC8: 統合タグ(are-sore)

```
スロット1: are-sore(0.80), kore(0.15)
スロット2: ookii(0.90)
```

出力:

```
整形結果: あれは大きいです
採用タグ: are-sore, ookii
```

所見: 統合タグは文脈が無いと「あれ/それ」のどちらかを機械的に選ぶしかない
(ここでは「あれ」が出た)。指示語の解決は本質的に映像文脈(指差し先)が必要で、
タグ列だけでは原理的に決められない。将来の非手指要素・空間参照の取り込み課題として記録。

## 総評

1. **成立している**: 1語素通し・過剰生成の抑止・活用補い・不確実性の明示(?)は
   v1 の指示で動く。①(プロンプト)として最低限の土台はできた
2. **挽回の発動条件が狭い**: top-k 挽回は「top-1 の組が破綻」しているときのみ。
   現語彙では日本語の許容度が高く、単語ペア程度では発動機会が少ない。
   ②へ投資する判断は、文(複数サイン)認識が動き出してからで十分
3. **救えない誤りの分界が明確**: 高確信度の単発誤り(左右手ゆれ由来)は部品Cの責任外。
   認識側の対策(データ増・特徴表現)と混同しないこと
4. **v2 候補**: 「?」の数値基準の明文化 / 語彙表に無い未知タグが来たときの挙動を
   ルールに追加(現状は未定義)/ 実際の `--predict-pose` 出力を機械的に写せる入力
   フォーマット(JSON)の受け付け

## 実データでの独立再検証(2026-08-14)

- 実施日: 2026-08-14
- 入力データ: `transformer_burn --eval-holdout data/pose_dict_full.json --mirror-augment --seed 1`
  の実出力(51語フルデータセット、未見テイク評価)から抜粋した実際の top-5(タグ+確率)
- 実行方法: TC1〜8(2026-07-02)は「プロンプトを書いた本人と同一セッションの LLM がその場で
  適用した」ため自己都合バイアスの懸念があった。今回は**会話履歴を共有しない独立したエージェント
  (Agent ツールで都度フレッシュに起動)6体にそれぞれ1件ずつ**、prompt_v1.md のシステムプロンプト
  本文(2026-08-14 時点の51語語彙表)と入力のみを渡し、指定の2行フォーマットのみを返させた。
  真の実行者(採点者である自分)は事前に正解ラベルを知っているが、**実行を担ったエージェント側には
  正解ラベルを一切渡していない**(本番の部品Cが正解を知らないのと同じ条件)
- あわせて `prompt_v1.md` 内の語彙表が stage 2 の words.tsv 変更(hai/iie→atteru/chigau、
  hanasu→iu、samui→samui-kowai、dekinai-muzukashii 追加など)に追随しておらず**同期漏れ**
  だったことが判明したため、このタイミングで51語に同期した(本節の入力はすべて同期後の版で実行)

### RC1: 高確信・正解(正常系の実データ確認)

```
スロット1: ii(1.00), tatoeba(0.00), miru(0.00), wakaru(0.00), onegaishimasu(0.00)
```
(正解: ii)

出力:
```
整形結果: いい
採用タグ: ii
```

所見: TC1・TC7 と同様、期待どおり素通しされた。

### RC2: 高確信の誤認識(正解: arigatou → 予測 otsukaresama 0.98)

```
スロット1: otsukaresama(0.98), arigatou(0.01), yomu(0.00), suki(0.00), samui-kowai(0.00)
```
(正解: arigatou)

出力:
```
整形結果: お疲れさま
採用タグ: otsukaresama
```

所見: TC2 と同じ結論を実データ・独立実行で再確認。**高確信度の単発誤りは部品Cでは救えない**
(認識側=部品Bの責任範囲)。

### RC3: 拮抗、かつ正解が候補外(正解: kanojo → 予測 kiku 0.50 / ok 0.49)

```
スロット1: kiku(0.50), ok(0.49), kanojo(0.00), sayounara(0.00), ni(0.00)
```
(正解: kanojo)

出力:
```
整形結果: 聞く
採用タグ: kiku?
```

所見: 0.50/0.49 の拮抗を検知して「?」を付与(ルール5どおり)。正解自体が候補に無いため
救えないのは想定内だが、**拮抗の検知は実データでも機能した**。

### RC4: 確率差 0.51(拮抗と判定されず、誤りをそのまま採用)

```
スロット1: onegaishimasu(0.75), watashi(0.24), tatoeba(0.00), kiku(0.00), ok(0.00)
```
(正解: watashi)

出力:
```
整形結果: お願いします
採用タグ: onegaishimasu
```

所見: **TC6 で指摘した「拮抗判断の閾値が不明確」という弱点が実データでも再現した**。
0.75/0.24(差0.51)は「?」が付かず最上位をそのまま採用。今回は誤りが最上位側だったため
結果的に救えなかったが、仮に正解が最上位でも僅差でない限り「?」が付かない一貫した挙動であり、
v2 候補(TC6所見: 差0.15未満で「?」等の数値基準の明文化)の必要性を補強する実例になった。

### RC5: 意味的に近接した高確信誤り(正解: kare → 予測 kanojo 1.00)

```
スロット1: kanojo(1.00), ok(0.00), ohayou(0.00), go(0.00), watashi(0.00)
```
(正解: kare)

出力:
```
整形結果: かのじょ
採用タグ: kanojo
```

所見: 代名詞の性(かれ/かのじょ)を取り違えた高確信誤りも、RC2 と同様に部品Cでは検知できない。
文脈(前後のスロット)が無い単発入力では、意味的に近い語であっても手がかりが無く当然の結果。

### RC6: 全候補がほぼ均等に低確信(モデルが実質「わからない」状態)

```
スロット1: ookii(0.00), kaku(0.00), yon(0.00), onegaishimasu(0.00), san(0.00)
```
(正解: konnichiwa、候補外)

出力:
```
整形結果: 大きい
採用タグ: ookii?
```

所見: TC4想定の「僅差の拮抗」とは異なる**「全体的に低確信」というケース**でも、最上位を採用しつつ
自発的に「?」を付けた。ルール5の「確率が拮抗して自信がない」を字面どおりの拮抗以外にも
妥当に一般化できていることの確認になった。正解自体が候補外のため救えないのは想定内。

### 実データ再検証の総評

1. **TC1〜8(2026-07-02)の結論は実データ・独立実行でも覆らなかった**: 高確信度の単発誤り
   (RC2・RC5)は部品Cでは救えず、これは一貫して部品B(認識モデル)の責任範囲であることが
   実データでも再確認された
2. **拮抗検知(ルール5)は実データでも機能**するが、**閾値の不明確さ(TC6の指摘)も実データで
   再現**(RC4: 差0.51で非検知)。v2 で数値基準を明文化する優先度がやや上がったと判断できる
3. 今回の入力はすべて実運用と同じ「文脈の無い単発スロット」(文認識未実装のため)。
   TC3 で確認した「top-k 挽回」の価値検証は依然として複数スロット入力が要る点は変わらず、
   **②(LoRA)投資判断は文(複数サイン)認識が動いてからで十分という結論も維持**
4. 独立実行によりバイアス懸念は概ね解消できたが、6件はいずれも1スロットの合成的実データ
   選抜であり、まだ n が小さい点は TC1〜8 と同様の限界として残る
