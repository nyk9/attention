# 部品C プロンプト v1 検証記録

- 実施日: 2026-07-02
- 実行モデル: claude-fable-5(Claude Code セッション内で prompt_v1.md を適用)
- **注意(検証の限界)**: この記録は「プロンプトを書いた本人(同一セッションの LLM)が
  その場で適用した」スモークチェックであり、評価者と実行者が文脈を共有しているため
  自己都合バイアスの可能性がある。本判定は **API 経由の独立実行(まっさらな文脈)** で
  行うこと。テストケースも n=8 の手作りで、頑健性の根拠にはならない

## テストケースと結果

TC2 は stage 1 の実評価(top-1 30%)で実際に起きた誤りをそのまま使っている。
他は語彙表(words.tsv 準拠)から構成した合成ケース。

### TC1: 1語・高確信(正常系)

```
スロット1: konnichiwa(0.99), ohayou(0.004), konbanwa(0.003)
```

出力:

```
整形結果: こんにちは
採用タグ: konnichiwa
```

所見: 期待どおり。1語はそのまま出て、文章に膨らまない(ルール4が効いている)。

### TC2: 高確信の誤認識(stage 1 実例: 正解 anata → arigatou 0.97)

```
スロット1: arigatou(0.97), onegaishimasu(0.02), sumimasen(0.005)
```

出力:

```
整形結果: ありがとう
採用タグ: arigatou
```

所見: 「ありがとう」と出るしかなく、**正解 anata が候補に無い誤りは整形側では救えない**。
これは想定どおりで、左右手ゆれ由来の高確信度誤りは認識側(部品B)の課題という
責任分界の確認になった。

### TC3: 文脈による top-k 挽回(部品Cの存在価値を測る中心ケース)

top-1 の組み合わせが意味的に破綻するように構成:

```
スロット1: sayounara(0.50), watashi(0.35), anata(0.10)
スロット2: taberu(0.90), nomu(0.07)
```

出力:

```
整形結果: わたしは食べます
採用タグ: watashi?, taberu
```

所見: 「さようなら+食べる」の破綻を検知して 2位の watashi を採用し、ルール5どおり
「?」が付いた。**ただしこの挽回は top-1 の組が明確に破綻しているときしか働かない**。
今の語彙(挨拶・代名詞・基本動詞の50語)では日本語がたいていの組を許容してしまう
(例: 「ありがとう、行きます」は不自然でない)ため、発動機会は限定的とみられる。
語彙の拡大と文長の増加で価値が上がる見込みで、②(LoRA)へ進む判断は stage 2 以降の
実文データで行うのが妥当。

### TC4: 確率拮抗

```
スロット1: hai(0.51), iie(0.49)
```

出力:

```
整形結果: はい
採用タグ: hai?
```

所見: top-1 採用+「?」で不確実性が伝わる。期待どおり。

### TC5: 挨拶の連続(2スロット)

```
スロット1: otsukaresama(0.90)
スロット2: sayounara(0.85)
```

出力:

```
整形結果: お疲れさまでした。さようなら。
採用タグ: otsukaresama, sayounara
```

所見: 活用・句読点の補い(ルール2)は自然。意味の追加はない。

### TC6: 通常の2スロット文

```
スロット1: watashi(0.85), anata(0.10)
スロット2: nomu(0.60), taberu(0.35)
```

出力:

```
整形結果: わたしは飲みます
採用タグ: watashi, nomu
```

所見: 正しく整形されたが、**nomu(0.60) vs taberu(0.35) に「?」が付かなかった**。
「拮抗」の判断が主観的なのは v1 の弱点(TC4 の 0.51/0.49 には付き、ここには付かない
境界が明文化されていない)。v2 では「top-1 と top-2 の差が 0.15 未満なら ?」のような
数値基準の明文化を検討する。

### TC7: 過剰生成の抑止

```
スロット1: sumimasen(0.95)
```

出力:

```
整形結果: すみません
採用タグ: sumimasen
```

所見: 期待どおり(「すみませんが、〜」のような続きを生成しない)。

### TC8: 統合タグ(are-sore)

```
スロット1: are-sore(0.80), kore(0.15)
スロット2: ookii(0.90)
```

出力:

```
整形結果: あれは大きいです
採用タグ: are-sore, ookii
```

所見: 統合タグは文脈が無いと「あれ/それ」のどちらかを機械的に選ぶしかない
(ここでは「あれ」が出た)。指示語の解決は本質的に映像文脈(指差し先)が必要で、
タグ列だけでは原理的に決められない。将来の非手指要素・空間参照の取り込み課題として記録。

## 総評

1. **成立している**: 1語素通し・過剰生成の抑止・活用補い・不確実性の明示(?)は
   v1 の指示で動く。①(プロンプト)として最低限の土台はできた
2. **挽回の発動条件が狭い**: top-k 挽回は「top-1 の組が破綻」しているときのみ。
   現語彙では日本語の許容度が高く、単語ペア程度では発動機会が少ない。
   ②へ投資する判断は、文(複数サイン)認識が動き出してからで十分
3. **救えない誤りの分界が明確**: 高確信度の単発誤り(左右手ゆれ由来)は部品Cの責任外。
   認識側の対策(データ増・特徴表現)と混同しないこと
4. **v2 候補**: 「?」の数値基準の明文化 / 語彙表に無い未知タグが来たときの挙動を
   ルールに追加(現状は未定義)/ 実際の `--predict-pose` 出力を機械的に写せる入力
   フォーマット(JSON)の受け付け
